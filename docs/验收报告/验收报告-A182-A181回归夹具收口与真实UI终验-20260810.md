- 表格和列设置都没有“系统库存/账面数量”，刷新后不变。

- 影响：A181 代码/回归证据不能替代本轮可见 UI 失败；必须在新任务中先确认运行页实际装载，再决定是产品代码还是运行构建问题。

## UI 结束后的只读归因

以下核对发生在 Chrome 真实用户终验结束后，不属于上述 UI 通过证据，也没有修改产品或测试代码。

- 当前 `admin / ADMIN` 具备 `finance.cash_transfer.audit`、`finance.settle` 和 `master.data.manage`；合格的已审核、启用 CNY/USD 账户也不止一条。因此本次管理员现场不能归因为账户状态、200 行分页或 ADMIN 缺少现行权限。
- `CashTransferForm.vue` 只在组件挂载时加载一次账户；失败或过滤为空后保留空数组，“新增”不会重载，也没有明确的 loading、empty 或重试状态。A163 浏览器段此前只打开页面和截图，没有断言账户 option，也没有用 UI 完成选值，故没有覆盖真实主链的这一前置步骤。
- 现有静态证据仍不能区分“候选请求非 200”“返回 200 但为空”或“响应有行但未进入组件状态”。新任务应先同时记录候选请求状态、响应行数和渲染后的 option 数，再决定修前端还是后端。
- 另有独立权限合同错位：页面和表单要求 `finance.cash_transfer.audit`，账户候选守卫只接受 `finance.settle`。这不是当前 ADMIN 现场的直接根因，但会阻断只获转账权限的自定义角色，权限验收时必须一并收口。
- 盘点当前源码明确透传 `showExecutedQtyColumn=true` 语义；5173 当前提供的 Vite 转译模块也包含该绑定且响应为 `no-cache`。A88 在干净浏览器上下文已断言系统库存单元格，A181 full 截图也显示“系统库存”。因此现场失败与当前代码/干净路径证据相矛盾，暂不能直接定性为仍存在的生产代码缺陷。
- 盘点下一步应先关闭旧页签并用全新 Chrome context 硬加载，核对表头、列设置和运行时 prop；若仍复现，再考虑在盘点表单对 `variant === 'count'` 显式传字面量 `true`，并给 A88 补“表头文字 + 列设置”断言。诊断前不应改后端或共享表格组件。
