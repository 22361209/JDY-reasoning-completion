## 后端更新合同

四类更新入口固定为：

```http
PATCH /api/master-data/{type}/{code}
Content-Type: application/json

{
  "version": 7,
  "changes": {
    "contact": null,
    "remark": "新备注"
  }
}
```

实现由 `MasterDataPatchService` 集中承担业务规则，Controller 只负责 HTTP 边界、权限和成功审计编排：

1. 外层只允许 `version`、`changes`，`version` 必须是非负整数，`changes` 必须是非空对象。
2. 每个类型拥有固定字段白名单和字段类型；字符串、布尔、非负数值、可空性均按 JSON 节点严格判断，不接受依赖字符串转换的宽松解析。
3. `code/systemNo/version/auditStatus/status/enabled` 不进入更新白名单；启禁用、审核和反审核仍只走正式独立动作。
4. 查询目标时锁定记录，先验证 `DRAFT` 和请求版本，再解析引用，最终单条 UPDATE 同时匹配记录、旧版本和 `DRAFT`；成功后版本递增并返回服务端规范化完整摘要。
5. 物料类别、单位、默认仓库、默认供应商和默认生产车间必须解析为真实、已审核且启用的引用；显示值与 UUID 成对更新或成对清空。
6. 任一字段、引用或 CAS 失败时整个事务回滚；A138 已实测无效默认仓库返回 400，原仓库和版本保持不变。
7. 成功更新记录 `MASTER_DATA/PATCH_MASTER_DATA` 操作日志，只记类型、编码、变更字段名和版本，不记录字段值或敏感内容；失败更新不产生成功日志。

四类旧 `PUT` 均返回 405；非本批的 `product-category`、`unit`、`production-department` 仍保留原 PUT，不被 A138 改造成另一套未验收合同。

## 前端行为

- 列表行携带不可见 `version`，编辑页保存独立原始快照和当前版本。
- 保存只比较可编辑字段；数字、布尔与显式清空保持正确 JSON 类型，未修改字段不进入 `changes`。
- 无变化时给出明确反馈且不发 PATCH；成功后以服务端规范化结果刷新表单、快照和版本。
- 409 不再统一伪装成“编码已存在”；页面展示服务端冲突原因，保留用户输入和 dirty 状态，用户可自行比对后再处理。
- 已审核资料不能直接进入可保存编辑态；存在未保存改动时，审核、反审核、启禁用和删除均被阻止。
- 客户、供应商、仓库的 `status` 编辑控件为只读，状态变化继续使用正式动作。
- `useMasterDataMaintenance` 中遗留的整表 PUT 编辑提交死路径已删除，正式页面与旧弹窗不再形成双写入口。
- 上述新增守卫只作用于 A138 四类资料；独立 review 发现并修复了“误伤三个旧 PUT 类型审核态编辑”的问题，复审确认范围已收紧。
