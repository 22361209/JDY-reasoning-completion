## 仍有结构债务

### P1. `DataListPage.vue` 仍是万能列表

当前约 2394 行。虽然筛选逻辑已拆出一层，但列表状态、列定义、批量动作、汇总、分页、视图切换仍集中在一个大文件里。

风险：后续再改销售/采购/库存列表列、汇总和动作时，仍可能牵一发动全身。

建议下一步拆分：

- `useListQueryState`
- `useListColumns`
- `useListBatchActions`
- `useListSummary`
- `useListViewMode`

### P1. `EntryTable.vue` 能力集中，维护成本上升

当前约 1636 行。它已经承担了分录高频能力，但继续增加字段、批量填充、日期、库存、键盘流后，风险开始上升。

建议下一步只拆内部 composable，不改外部调用合同：

- 列定义与列设置
- 单元格键盘流
- 批量填充
- 主数据匹配选择
- 行合计/底部汇总

这样能保持销售/采购页面不受影响。

### P1. 生产计划表体不是完整多行分录

`ProductionPlanEntryTable.vue` 当前是专用表体，已经有列设置/筛选/列宽，但没有像销售分录一样的行加减按钮。当前后端模型也更接近“一张计划单一个母件计划”。

如果业务方向确定为“一张生产计划可多行母件”，需要后端模型、API、前端表体和下推逻辑一起升级，不能只补前端按钮。

### P1. 单据生命周期逻辑仍有重复

大多数单据走 `useDocumentModule`，但销售出库仍有 `useSalesOutDocument` 这种专用大 composable，里面包含保存、审核、反审核、删除、作废、源单选择、键盘流等大量重复逻辑。

风险：动作规则以后改一次，仍可能漏掉专用单据。

建议把“单据生命周期 + 源单占用 + 输出 + 键盘流”继续沉淀到共享层，专用 composable 只保留销售出库自己的业务差异。

### P2. BOM / 生产计划是“共享合同对齐”，不是“完全复用 EntryTable”

这是当前报告必须说清楚的边界。它们已经不再是完全野生表格，但还不是销售/采购分录那套完整 `EntryTable`。

是否要继续强行并入 `EntryTable`，需要看业务差异：

- BOM 是产品结构，不是业务单据分录。
- 生产计划目前是计划行，不是出入库执行分录。

短期更稳的路线是：保留专用组件，但必须持续复用 `TableCoreHeaderCell`、列设置、筛选、列宽、行按钮视觉。

### P2. `SourceSelectorDialog` 还不是完整共享表格

它已经解决“每页手写源单弹窗”的问题，但内部仍是简单 `<table>`。

短期可接受，因为源单弹窗目前只需要搜索、勾选、列设置、确认。

后续若要在源单弹窗内做列筛选、拖拽列宽、固定列、明细汇总，就应迁入 `TableCore`。

### P2. 主数据选择弹窗和部分设置页仍是原生表

例如：

- `MasterSelectorDialog.vue`
- `OpeningStockPage.vue`
- `NumberingRuleSettingsPage.vue`

这些不是核心单据分录，短期可以接受。但如果用户开始频繁在这些页面录入或筛选，应该按共享表格合同改造。

### P2. `StandardDocument` 的 testid 仍带销售订单历史命名

例如 `save-sales-order`、`audit-sales-order`、`delete-sales-order`。功能上不影响当前回归，但长期看会误导后续脚本和接手者。

建议在下一轮低风险改名时，同时兼容旧 testid 一段时间，避免回归脚本大面积断。
