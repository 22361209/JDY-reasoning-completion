# A119 完整多账套架构迁移计划

本文是 A119 的防跑偏计划。A119 不是新增页面批次，而是一次横切架构迁移：从 A117 的单数据库账套上下文过渡层，升级到共享应用容器 + 平台库 + 账套数据隔离。

## 目标架构

```text
frontend 容器
backend 容器
redis 容器
postgres 容器
        |
        ├── platform_db       用户、账套列表、登录、权限入口
        ├── tenant_bld_2026   博莱德账套
        ├── tenant_test       测试账套
        └── tenant_history    历史账套
```

容器始终运行。切换账套时不启动/停止容器，只切换后端 session/request 上的账套上下文；前端刷新工作台并关闭或重置旧账套页签，避免旧上下文误操作。

## 不变底线

- 不拆微服务，不按账套启动多套应用容器。
- Redis 仍只缓存登录态；业务数据、库存、单据状态、报表不缓存。
- 保存只落草稿，审核后才影响库存、资金、选源、下推和后续业务链。
- 业务隔离必须以后端为准，前端只能显示和预防误操作。
- 底层关联继续使用 UUID，不用业务编码或系统编号做外键。
- 不重跑 `build-jdy-feature-approval.mjs`，不手改任何生成物。
- A119 期间发现非账套相关体验问题，除非阻断迁移，否则记录到后续批次，不顺手扩散。

## 阶段拆分

### A119-0 基线与清单

目的：防止一开工就把多账套、初始化、列表 SQL、业务逻辑混在一起。

交付物：

- A118 已单独提交，A119 从干净基线开始。
- 表归属清单：platform 表、tenant 表、共享/待定表。
- API 归属清单：平台 API、账套业务 API、跨账套管理 API。
- SQL 风险清单：直接 `JdbcTemplate`、列表汇总、报表、库存、编号、初始化。
- 确认本阶段采用“独立 database”还是“独立 schema”。默认按目标架构理解为独立 database；若实现成本过高，可在本阶段明确改为 schema，不允许中途静默摇摆。

验收：

- 文档列出所有核心表和核心 API 的归属。
- 找到所有必须接入账套路由的 SQL 入口。
- 未改业务逻辑，最多做轻量探针脚本。

### A119-1 平台层

目的：把用户、账套、登录、权限入口从业务账套数据里拆出来。

交付物：

- 平台库或平台 schema 承载用户、账套、账套授权、登录入口、权限入口。
- `sys_account_set` 升级为平台账套配置，包含数据库/schema、附件前缀、Redis 前缀、初始化状态。
- 登录选择账套时校验用户是否有权进入该账套。
- 当前账套信息由 session/request 统一提供，不由前端拼接。

验收：

- 管理员和普通用户可见账套范围不同。
- 无账套或无权限时，业务 API 被后端阻断。

### A119-2 TenantContext 与数据路由

目的：先有统一路由骨架，再迁业务模块。

交付物：

- 后端请求级 `TenantContext`。
- 数据库路由层：按当前账套选择目标 database/schema。
- Flyway/初始化策略：新账套创建时可初始化 tenant 结构。
- Redis key 统一带账套前缀。
- 附件路径统一带账套前缀。

验收：

- 两个测试账套能连接到不同数据边界。
- 故意切账套后查询同一业务接口，能证明数据来源不同。
- 没有账套上下文的业务请求失败。

### A119-3 账套初始化与种子数据

目的：让新账套可创建、可初始化、可清空业务数据。

交付物：

- 新建账套流程。
- 初始化当前账套流程。
- 开发期允许清空当前账套业务数据，保留平台用户、权限、账套配置。
- 主数据/BOM/编号默认规则的初始化策略明确。
- 在 Flyway 拆成 platform/tenant 迁移前，允许以 `tenant_*` schema 作为本地过渡边界；该决定必须写入阶段说明，不能误称为最终 database 完成。

验收：

- 新账套初始化后可登录、可进入工作台、可维护主数据。
- 清空当前账套不会影响其他账套。

### A119-4 业务模块迁移

按风险从低到高逐模块迁移，不跨模块乱改。

迁移顺序：

1. 主数据、单位、类别、BOM、编号规则。
2. 库存期初、库存余额、库存流水。
3. 销售链：报价、订单、发货通知、销售出库。
4. 采购链：采购申请、采购订单、采购入库、采购退货。
5. 生产链：生产计划、生产任务、领料、产品入库、齐套分析。
6. 委外链：委外加工、发料、入库、退货、报废。
7. 报表/列表汇总/导出。

每个模块交付物：

- 表结构或路由已进入账套边界。
- 列表、详情、保存、审核、反审核、选源、下推都只看当前账套。
- 编号、库存、源单占用、快照不串账套。

验收：

- 两个账套允许存在相同业务编码，但互不干扰。
- 账套 A 的单据不能选到账套 B 的源单。
- 账套 A 的库存审核不改变账套 B 的库存余额/流水。

### A119-5 前端账套隔离体验

目的：防止用户在旧页签里误操作旧账套上下文。

交付物：

- 登录页账套选择和记忆逻辑保留。
- 右上角账号菜单可切换账套。
- 切账套前检查未保存页签，提示用户确认。
- 切账套后关闭业务页签或强制刷新工作台。
- 页签/工作台清晰显示当前账套。

验收：

- 切账套后旧业务页签不再保留可编辑状态。
- 未保存单据切账套有提示。

### A119-6 运维能力

目的：多账套不只是能切，还要能维护。

交付物：

- 按账套备份/恢复方案。
- 按账套附件目录或对象存储路径。
- 按账套初始化、禁用、查看状态。
- 操作日志记录账套信息。

验收：

- 可以单独备份/恢复某个测试账套。
- 操作日志能看出用户在哪个账套做了什么。

### A119-7 回归与验收

目的：证明没有串账套。

必测：

- `cd backend && JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./mvnw test`
- `npm --prefix frontend run build`
- `node scripts/run-regression-tier.mjs smoke`
- 新增 A119 隔离回归脚本：两个账套、同物料编码、同单据类型、不同库存和不同编号流水，互不影响。
- 至少覆盖主数据、库存、销售、采购、生产、委外各一条隔离链路。

验收：

- 业务链路全在当前账套内闭环。
- 跨账套数据泄漏为 0。
- 文档更新 `docs/09`、`docs/12`，并归档 A119 验收报告。

## Goal 模式防跑偏规则

每个 goal 只做一个阶段或一个模块，不跨阶段顺手改。

开工前：

1. 读 `CLAUDE.md`、`docs/09`、`docs/12`、本文。
2. 明确本次 goal 是 A119-几。
3. 先列本阶段会改哪些模块、不会改哪些模块。

执行中：

- 发现非本阶段问题，记录到“后续问题”，除非阻断本阶段，否则不修。
- 每次改动优先沉淀共享层：TenantContext、路由、初始化、脚本 helper，不复制粘贴到每个模块。
- 每个模块迁移后立刻补最小隔离断言，不等全量结束才测。
- 不用前端隐藏问题；所有隔离和权限必须后端阻断。

收尾时：

- 更新 `docs/12` 阶段勾选。
- 更新 `docs/09` 当前快照。
- 写明测试命令和结果。
- 阶段完成才 commit；不要把多个未完成阶段塞进同一个提交。
