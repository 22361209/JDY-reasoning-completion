# 新项目可行性与迁移蓝图

更新日期：2026-06-28

## 结论先行

新开项目**可行，而且长期可能更干净**。但不建议直接抛弃当前项目裸开。更稳的路线是：

1. 先把当前项目中已经验证过的业务规则、字段地图、表格交互、测试分层和架构边界整理成“迁移资产”。
2. 新建一个干净代码项目，用轻量 `BillDefinition` / `MasterDataDefinition` 从第一天驱动单据、列表、分录和动作。
3. 先只做销售报价单 → 销售订单样板，2-3 天内验证新架构是否真的减少调整成本。
4. 如果样板成立，再迁销售链、采购链、主数据、生产链；如果样板不成立，停止新项目，回到当前项目局部重构。

本蓝图的目标不是马上重写全部 ERP，而是判断“新项目是否值得开”和“开了以后怎么不重走旧路”。

## 为什么现在会想到新开项目

当前项目已经跑出大量业务闭环，这是优点；但也积累了几个结构性负担：

- `DataListPage.vue` 承载太多列表定义、视图逻辑、按钮和列状态。
- 单据表单、分录表、动作条、源单关系靠页面 prop 和局部判断拼起来。
- 字段命名和显示规则散落在列表、分录、服务返回、回归脚本里。
- 需求从“复刻视觉”逐渐变成“沉淀长期 ERP 架构”，旧项目早期的快速实现开始拖慢后续决策。
- 每次小字段调整都要担心影响销售、采购、生产、主数据和回归脚本。

这不是某个文件写坏了，而是项目从“探索复刻”进入“产品骨架定型”阶段后的自然分叉。

## 三种选择

### 方案 A：继续在当前项目内重构

适合：希望最快保持现有功能可用。

优点：

- 已有后端业务、数据库迁移、登录权限、库存过账、源单链路、回归脚本可直接用。
- 不需要重新搭服务、登录、数据种子和基础页面。
- 风险主要是局部回归风险，不是从零风险。

缺点：

- 旧结构会拖慢元数据层落地。
- 大文件和历史兼容逻辑难以一次清干净。
- 容易继续出现“这里补一点、那里补一点”。

估计：A115 全部做完 4-6 天，且仍会保留部分历史包袱。

### 方案 B：直接新开正式项目

适合：确认要把它作为长期正式产品重新设计。

优点：

- 可以从第一天按定义层、模块边界、共享表格、动作规则、测试分层来做。
- 能丢掉旧的上帝组件、巨型列表、临时字段补丁和历史批次命名混乱。
- 更容易形成新人可接手的工程结构。

缺点：

- 短期业务闭环会倒退，需要重做登录、布局、接口、数据库、回归。
- 如果迁移资产没整理好，新项目可能只是换个目录重新堆债。
- 当前项目已经实现的细节很多，漏搬规则会导致业务倒退。

估计：2-3 天做出销售报价单 → 销售订单样板；7-10 天恢复销售/采购/主数据/生产的主要可用面；更完整替换当前项目要更久。

### 方案 C：新项目孵化，当前项目保留

适合：当前最推荐。

做法：

- 当前项目冻结为“可运行参考实现 + 规则来源 + 回归参考”。
- 新项目只先做薄样板，不承诺马上替换。
- 样板验证通过后，再决定是否持续迁移。

优点：

- 不赌全部项目。
- 允许新架构干净起步。
- 当前项目仍可随时提供业务参考和对照页面。

缺点：

- 短期会同时存在两个项目。
- 需要明确“当前项目只修阻断问题，不继续大扩展”，否则两边都累。

## 推荐决策

推荐选 **方案 C：新项目孵化，当前项目保留**。

理由：

- 当前项目有价值，但不适合继续无限加功能。
- 新项目的价值必须由销售报价单 → 销售订单样板证明，而不是先规划一大堆。
- 2-3 天可验证，不会沉没太多成本。

## 当前项目哪些资产要搬

### 必搬：业务规则

来源：

- `docs/guides/business-rules.md`
- `docs/guides/action-button-rules.md`
- `docs/06-数据一致性与库存原则.md`
- `docs/07-模块契约与边界.md`
- `docs/guides/bill-metadata-roadmap.md`

必须搬的规则：

- 只缓存登录态，业务数据不缓存。
- 审核才动库存、资金和执行状态；保存只产生草稿。
- 库存双写：流水 + 余额，同事务写入。
- 源单剩余量按非作废下游占用计算，草稿/未审核/已审核均占用。
- 销售报价单是价格承诺候选，不自动覆盖正式成交价。
- 报价有效期必填，过期自动失效。
- 销售订单选源单选择销售报价单。
- 发货通知单选源单选择销售订单。
- 销售出库单选源单选择发货通知单。
- 采购入库单选源单选择采购订单。
- 生产第一版走自发生产计划 → 生产任务 → 用料快照 → 领料 → 入库。
- 生产领料读取任务用料快照，不运行时直接读标准 BOM。
- 删除只允许已保存草稿，未保存单据直接关闭或新增放弃。

## 新项目技术栈建议

保持当前方向，不为了重开而换栈：

- 后端：Java 21 + Spring Boot 模块化单体。
- 数据库：PostgreSQL。
- 迁移：Flyway。
- 前端：Vue 3 + TypeScript。
- 表格：继续原生共享表格内核，但从第一天按 `TableCore` 组件化；如果后续发现原生表格成本过高，再评估成熟表格库，不在 P0 决策中引入。
- 缓存：只缓存登录态；业务数据直查数据库。
- 异步：第一版本地 outbox，不上 MQ。

## 新项目第一阶段目标

第一阶段不要追求全 ERP，只做一个垂直样板：

```text
物料/客户基础资料
  → 销售报价单
  → 销售订单
```

这个样板必须证明：

- 字段来自 `BillDefinition`。
- 列表整单/明细视图来自 `BillDefinition.listViews`。
- 分录列来自 `BillDefinition.entryColumns`。
- 动作条来自 `BillDefinition.toolbarActions` + 状态/权限判断。
- 源单关系来自 `sourcePolicy`。
- 销售报价单没有源单列，销售订单可以引用报价单。
- 修改字段文案只改定义，不全项目搜索替换。

## 新项目前 10 个任务

1. 初始化仓库、文档、dev 脚本和空壳服务。
2. 建立前端 `metadata` 定义层类型和字段片段。
3. 建立后端核心表：物料、客户、销售报价单、销售订单、操作日志。
4. 建共享表格 `TableCore`，支持列宽、横滚、列设置、筛选基本骨架。
5. 建共享单据容器 `DocumentPage`，支持动作条、表头、分录、合计。
6. 做物料/客户最小主数据建档和选择器。
7. 做销售报价单：保存、审核、有效期、设为有效/失效、列表/明细视图。
8. 做销售订单：选报价单源单、保存、审核、列表/明细视图。
9. 建第一批回归：smoke、报价单、销售订单、定义层字段一致性。
10. 复盘是否继续迁发货通知/销售出库，或回到当前项目内重构。

## 2-3 天验证计划

### 第 1 天

- 新项目初始化。
- 定义层类型、字段片段。
- 共享表格和单据容器雏形。
- 物料/客户最小数据。

### 第 2 天

- 销售报价单完整样板。
- 销售订单能从报价单选源单。
- 跑前端构建和基础后端测试。

### 第 3 天

- 补列表整单/明细视图。
- 补回归脚本。
- 对比当前项目：同样字段调整在新项目里是否只改定义。
- 给出继续/停止决策。

## 是否替换当前项目的判定标准

只有同时满足以下条件，才继续推进新项目：

- 销售报价单和销售订单样板可以跑通。
- 字段文案、源单列、动作按钮至少 80% 由定义层控制。
- 代码结构明显比当前项目少绕路。
- 新增一个字段不需要同时改 5 个以上非业务文件。
- 回归脚本比当前项目更稳定，能按 area 分层跑。

不满足则停止新项目，把产出的定义层经验回灌当前项目。

## 风险

- 新项目会短期降低可见功能数量。
- 如果用户继续在当前项目提新功能，两边会分叉。
- 当前项目中已有很多细节，迁移时容易漏规则。
- 定义层如果做太大，会变成新的平台包袱。

## 建议执行边界

如果启动新项目孵化：

- 当前项目只修阻断问题，不再做大功能。
- 新项目第一阶段只做销售报价单和销售订单。
- 所有规则先写文档，再写代码。
- 每天收尾写迁移日志。
- 未经确认，不删除当前项目。
