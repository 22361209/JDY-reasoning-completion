# 多账套与初始化说明

## 长期目标

采用共享应用容器、按账套隔离数据的路线：

```text
frontend 容器
backend 容器
redis 容器
postgres 容器
        |
        ├── platform_db       用户、账套列表、登录、权限入口
        ├── tenant_bld_2026   博莱德账套
        ├── tenant_test       测试账套
        └── tenant_history    历史账套
```

容器始终运行；用户切换账套时，不启动或停止容器，只切换后端 session/request 上的 `account_set`。前端切换后刷新工作台，避免旧页签继续编辑旧账套上下文的数据。

## 当前实现边界

当前实现已完成 schema-first 多账套路由：

- `public` 平台域保存账套、用户、授权、登录与平台级安全事实；每个账套的业务数据位于独立 `tenant_*` schema。
- 登录页输入账号密码并选择账套；认证后服务端只允许切换到当前用户被授权的账套。
- 右上角账号菜单提供账套切换和账套初始化入口；切换会刷新工作台并避免旧业务页签继续使用旧上下文。
- 业务 JDBC、附件路径和 tenant Redis key 均由当前认证账套上下文路由；业务表不以客户端提交的账套编码决定目标 schema。
- A137 将 tenant schema 的受管表和关键约束纳入版本化同步、唯一登记与 fail-closed 校验。

当前仍不是每账套独立 PostgreSQL database 的最终部署形态；`platform_db + tenant_* database` 是后续架构演进，而不是已交付能力。

## 登录前公开边界与认证后路由

- 匿名 session DTO 必须精确为 `{"authenticated":false}`。
- 匿名账套列表用于登录页选择，只暴露 `code/name`；目标数据库、schema、附件和 Redis 前缀等路由字段属于认证后数据。
- 用户认证后，后端只能返回并切换到该用户已授权的账套；客户端提交的账套编码不能代替服务端授权判断。
- 登录成功后，前端必须在展示工作台前重拉认证用户的授权账套；登出、session 失效和跨标签页失效后清空认证集合并恢复公开选择。
- 密码找回和其他登录前安全门禁没有当前账套上下文，必须使用平台级安全 Redis 前缀，不能借用 `sys_account_set.redis_key_prefix` 或 tenant 路由。

## 筛选预设的账套轴与用户轴

列表筛选预设的账套归属与创建者归属是两个独立维度。新建预设时，`created_by` 必须由服务端写入当前认证用户不可变 UUID，不能信任请求体传入的用户标识；后续更新不得改写该值。旧行的 `created_by IS NULL` 保持兼容，更新旧行也不回填。A135 基线中的 136 条 legacy 预设迁移数为 0，不执行批量归属推断。

## 初始化规则

本账套初始化仅管理员可见，必须手工确认执行。开发期允许清空当前项目业务数据，保留：

- 用户、角色、权限。
- 账套配置。
- 主数据、物料类别、计量单位、BOM。

清理范围：

- 业务单据。
- 库存期初、库存流水、库存余额。
- 编号流水。
- 编辑锁和列表筛选预设。

## 后续迁移门槛

进入正式多库账套隔离前，至少要完成：

1. 拆出 `platform_db`。
2. 每个账套独立 `tenant_*` 数据库或 schema。
3. 后端请求级数据源路由。
4. 附件按账套目录/桶隔离。
5. 账套业务 Redis key 统一带账套前缀；登录前平台安全门禁使用独立平台前缀。
6. 备份/恢复按账套执行。
