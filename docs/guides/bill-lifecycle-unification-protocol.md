# BLD 单据生命周期统一协议

本文件定义正式单据的统一生命周期口径。它是 `docs/guides/business-rules.md` 与 `docs/guides/action-button-rules.md` 的执行细则，后续新增单据必须先落到本协议，再决定页面按钮和后端业务处理。

## 核心状态

正式单据只使用三组生命周期状态：

| 状态组 | 字段 | 合法值 | 含义 |
| --- | --- | --- | --- |
| 主状态 | `status` | `DRAFT` / `AUDITED` / `VOID` / `RED_REVERSED`，历史兼容 `REVERSED` | 保存、审核、作废、红冲的主线状态；新反审核逻辑不再写入 `REVERSED` |
| 关闭状态 | `close_status` | `OPEN` / `CLOSED` | 连续执行类单据是否停止后续执行 |
| 关闭模式 | `close_mode` | `AUTO` / `MANUAL` / 空 | 销售订单关闭来源；自动关闭由执行事实触发，手动关闭由用户确认剩余不再执行 |
| 冻结状态 | `frozen_status` | `NORMAL` / `FROZEN` | 连续执行类单据是否暂停后续使用 |

不得再新增独立的 `execution_status` 作为生命周期来源。列表上的出库状态、入库状态、已执行数量、未执行数量等只属于执行事实或展示派生值，不决定按钮是否合法。`outStatus` / `inStatus` 只能用于展示，按钮可用性和下推资格必须看未出库数量、未入库数量、可下推数量等事实字段。

`REVERSED` 只作为历史兼容/旧数据展示状态。新业务逻辑执行反审核时，统一从 `AUDITED` 回到 `DRAFT`；真正不可逆或冲销类场景走红冲/红字单，不再用 `REVERSED` 表达新状态。

## 基本转换

| 动作 | 前置条件 | 结果 | 说明 |
| --- | --- | --- | --- |
| 保存 | 未保存或草稿 | `DRAFT` | 只保存草稿，不影响库存、资金、源单执行量 |
| 审核 | `DRAFT` | `AUDITED` | 审核后才产生业务事实，由各单据 AppService 写库存、应收应付或快照 |
| 反审核 | `AUDITED` 且无下游阻断 | `DRAFT` | 反审核必须回退审核产生的业务事实；不写入 `REVERSED` |
| 作废 | 已保存草稿且单据策略允许作废 | `VOID` | 必须填写原因并用当前账号密码确认；前后端同一 `voidAllowed` 策略，后端必须强校验 |
| 关闭 | 已审核、未关闭、未冻结且单据支持关闭 | `close_status=CLOSED` | 只适用于连续执行类单据；销售订单手动关闭必须写入 `close_mode=MANUAL` 和关闭原因 |
| 反关闭 | 已审核、已关闭且单据支持关闭 | `close_status=OPEN` | 恢复后续执行资格；销售订单只允许反关闭 `close_mode=MANUAL` |
| 冻结 | 已审核、未关闭、未冻结且单据支持冻结 | `frozen_status=FROZEN` | 暂停后续选源、下推、执行 |
| 解冻 | 已审核、已冻结且单据支持冻结 | `frozen_status=NORMAL` | 恢复使用资格 |
| 红冲 | 已审核且单据支持红冲 | 创建红字/退货/冲销单据 | 只适用于库存/财务事实类单据；红字单据保存仍是草稿，审核才产生反向业务事实 |

## 红冲生命周期口径

红冲不是撤销原单，而是新增一笔可审计的反向事实。它只适用于原单已审核、原单已经产生库存/应收/应付/发票/生产/出入库等事实影响，且原单不能安全反审核或不能直接撤销的场景。

- 红冲必须创建新的红字/退货/冲销单据；新单据有自己的单号和生命周期。
- 红字单据保存只落草稿，不动库存、资金、应收应付或生产执行量；审核红字单据时才产生反向业务事实。
- 红字单据必须记录来源单、来源行、来源数量和来源金额。
- 红字草稿的物料、仓库、来源行、数量、单价、金额、税额等业务事实字段按来源单反向快照生成，页面应只读；后端审核仍必须按来源单重新校验。
- 来源单存在非作废红字单时，来源单不得反审核、作废或再次红冲；必须先删除/作废红字草稿，或反审核并处理已审核红字单后，才能回到来源单直接撤销路径。
- 审核红字单据时，必须校验来源单仍为已审核，并校验红字行没有改物料、仓库、来源行、数量、单价、金额、税额等反向事实。当前全单红冲模型要求红字行与来源行一一反向一致；未来若启用部分红冲，必须先补来源行累计红冲数量/金额字段和剩余可冲计算。
- 审核红字单据后，才允许回写或计入来源单累计红冲数量/金额。
- 不允许重复红冲超过来源单剩余可冲数量/金额；审核红字单据时必须重新校验来源剩余可冲余量。
- `非作废红字单` 指同一来源下 `status <> VOID` 的红字单据，用于防止重复创建草稿或重复占用红冲流程；它不等同于已生效。
- `已生效红字单` 指已审核红字单据；历史兼容状态 `RED_REVERSED` 按已生效红字单处理。只有已生效红字单参与来源单累计红冲数量/金额和正式剩余可冲余量计算。

## 单据能力分类

| 类别 | 单据 | 关闭/冻结 | 行关闭/行冻结 | 红冲 | 作废 |
| --- | --- | --- | --- | --- | --- |
| 报价候选 | 销售报价单 | 否 | 否 | 否 | 是 |
| 连续执行承诺 | 销售订单、发货通知单、采购订单 | 是 | 发货通知单、采购订单保留；销售订单新业务不再暴露行关闭，行关闭 API 已禁用，仅保留字段兼容 | 否 | 是 |
| 库存/执行事实 | 销售出库单、采购入库单、生产领料单、产品入库单 | 否 | 否 | 是 | 是 |
| 普通库存事实 | 采购退货单、其他入库单、其他出库单、调拨单、盘点单、盘盈单、盘亏单 | 否 | 否 | 否 | 是 |
| 资金核销事实 | 收款单、付款单 | 否 | 否 | 否；退款另单后续实现 | 否；草稿可删、审核后只能反审核 |

第一版共享 `BillLifecycleController` 只负责上表中的正式业务单据。BOM、生产计划、生产任务、采购申请、委外加工链路可以使用同样口径，但如果尚未接入共享控制器，必须在各自 AppService 中执行同样前置规则：保存只草稿，审核后才可用，未审核不得选源或下推。

当前未完整接入共享生命周期控制器的 BOM、生产计划、生产任务、采购申请、委外链路，不计入“全 ERP 生命周期 100% 完成”。它们必须按本协议继续回收：动作按钮、状态规则、列表字段、后端守卫和测试逐批补齐。

收款单和付款单使用共享状态口径与前后端能力登记，但审核/反审核必须走 finance 专用 AppService：普通状态 UPDATE 无法原子核销或释放多张 AR/AP，不得把通用 `BillLifecycleService` 当成结算引擎。

### A141 收付款登记记录

| 字段 | 收款单 | 付款单 |
| --- | --- | --- |
| 单据类型 | `receipt` / `ar_receipt` / 收款单 | `payment` / `ap_payment` / 付款单 |
| 列表 key | `ar-receipt-form-list` | `ap-payment-form-list` |
| 详情页/表单组件 | 共享 `SettlementDocumentForm` + `StandardDocument` / `ActionBar` | 同左 |
| AppService / Controller | `FinanceSettlementAppService` / `FinanceSettlementController` | 同左 |
| 审核 | 是；锁单据及全部应收后原子核销 | 是；锁单据及全部应付后原子核销 |
| 反审核 | 是；释放应收并回 `DRAFT` | 是；释放应付并回 `DRAFT` |
| 作废/关闭/冻结/行级动作 | 均否 | 均否 |
| 红冲/退款 | 否；F081 后续独立退款单 | 否；F083 后续独立退款单 |
| 下推/选源事实 | 销售出库只预填；使用应收实时未核销金额 | 采购入库只预填；使用应付实时未核销金额 |
| 历史兼容 | AUDITED legacy 头/明细只读且不可删除；可安全反审核，补真实账户后再审 | 同左 |

两类单据的草稿不占来源余量，审核是最终守卫；0 元草稿无需原因即可保存但不能审核，负数草稿不得保存，重复审核必须幂等。单据头、来源和 A140 财务账户必须同为 CNY 或同为 USD，生命周期不得触发汇率换算或跨币种核销。

## 未成熟模块边界

下列模块已经开始收紧生命周期口径，但尚未完整接入共享生命周期控制器。它们不是豁免项，只是接入边界：

| 模块 | 当前边界 | 已收紧口径 | 后续接入条件 |
| --- | --- | --- | --- |
| BOM | 仍走生产模块专用 AppService 和专用表体 | 审核后才可被生产计划/委外等引用，反审核回 `DRAFT` | 可用化后登记单据类型、列表 key、后端目标表和按钮能力 |
| 生产计划 | 仍有专用计划分解和下推规则 | 保存只草稿，审核后才允许下推生产任务/采购申请 | 生产计划列表和详情动作统一由生命周期能力表驱动 |
| 生产任务 | 当前仅局部可用，未完整接入共享生命周期 API | 不允许另起 `REVERSED` 新状态 | 任务下推领料和用料快照稳定后再接共享动作守卫 |
| 采购申请 | 仍是生产计划下推链路里的新模块 | 未审核不得被采购订单选源 | 形成正式列表、详情页和选源事实字段后登记能力 |
| 委外链路 | 委外加工、发料、入库、退货、报废已有专用 AppService；旧“委外表面处理”仍是边界页面 | 新反审核路径已回 `DRAFT`；未审核不得作为下游事实 | 委外正式链路稳定后逐单登记；旧表面处理页面不得扩展为新生命周期规则来源 |

这些模块进入下一轮可用化改造时，必须接入本协议，不允许另起一套状态体系、按钮体系或下推判断体系。已经局部做到“反审核回 `DRAFT`”的，只能说明口径收紧，不代表完整接入。

### 生命周期权限

- 共享生命周期 API 必须使用 `@RequireDocumentPermission`，由 `DocumentPermissionPolicy` 根据 `{type}` 映射到该单据现有模块权限；权限检查发生在 `BillLifecycleService` 修改状态、版本、分录或成功业务日志之前。
- `BillLifecycleController` 登记的每一个 type 都必须在权限表中有且只有一项映射，权限表也不得出现没有 Controller target 的孤立 type。
- 单据锁 status/acquire 复用同一权限表，防止无权用户读取持锁人或抢占无权单据；release 只释放当前 session 本人持有的锁，override 继续要求 `document.lock.override`。
- 前端隐藏或禁用动作不构成权限；低权限直接调用生命周期和锁 URL 必须返回 403 且业务事实、状态、版本、锁和成功业务日志不变。

## 源单与下推

- 源单和源单行必须同时满足：主状态 `AUDITED`、关闭状态 `OPEN`、冻结状态 `NORMAL`、行关闭状态 `OPEN`、行冻结状态 `NORMAL`。
- 未审核源单不得被选源、下推或执行。
- 已关闭、已冻结、行关闭、行冻结的源单行不得继续作为可用来源。
- 下推按钮、选源弹窗和批量执行按钮不得依赖 `outStatus` / `inStatus` 这类中文展示状态。它们必须依赖未出库数量、未入库数量、可下推数量、行关闭/冻结状态等事实字段。
- 源单余量遵守“只有审核才产生业务事实”：下游草稿、已保存未审核单据不扣减正式可执行余量。选源弹窗可以用临时锁或编辑中提示防止多人同时编辑，但不得把草稿当业务事实扣量。
- 审核是最终守卫：所有带源单行和数量的下游单据，审核时必须按“源单号 + 源行号”汇总本单分录，再与已审核下游占用后的源单剩余量比较；合计超出时审核失败。该守卫由 `BillLifecycleService.guardSourceLineQuantities` 统一承载，不能在某一张单据里私写一套。
- 当前已接入统一审核汇总校验的链路：销售订单 -> 发货通知单、发货通知单 -> 销售出库单、采购订单 -> 采购入库单、采购入库单 -> 采购退货单。
- 销售订单 -> 发货通知 -> 销售出库链路中，销售订单列表/详情的未出库数量以“销售订单数量 - 已出库数量”为准；发货通知选源可通知量以“销售订单数量 - 已审核发货通知数量”为准。草稿发货通知不占用可通知量；发货通知审核时必须按同一源销售订单行汇总本单数量，合计超出剩余可通知量则审核失败。
- 销售出库分录必须同时保留两层来源：`sourceOrderNo/sourceLineNo` 表示原销售订单，`sourceDeliveryNoticeNo/sourceDeliveryLineNo` 表示直接来源发货通知。列表可用 `sourceBillNo` 展示直接来源发货通知，但详情/API 不能把发货通知号覆盖到 `sourceOrderNo`。

## 销售订单关闭口径

本轮只收口销售订单链路，不全局删除行关闭字段；销售订单行关闭 API 先禁用，其他单据行关闭是否继续保留另开任务。

销售订单业务上只暴露整单关闭/反关闭。关闭状态展示为：

| 数据状态 | 展示 |
| --- | --- |
| `close_status=OPEN` | 未关闭 |
| `close_status=CLOSED` 且 `close_mode=AUTO` | 自动关闭 |
| `close_status=CLOSED` 且 `close_mode=MANUAL` | 手动关闭 |
| `close_status=CLOSED` 且 `close_mode` 为空或历史未知 | 历史已关闭 |

自动关闭规则：

- 当销售订单所有分录 `remainingQty = qty - shipped_qty = 0` 时，系统自动写入 `close_status=CLOSED`、`close_mode=AUTO`、`close_reason=全部出库，系统自动关闭`。
- 自动关闭不需要用户输入原因，也不能被用户手动反关闭。
- 如果销售出库反审核、红冲等导致 `remainingQty > 0`，且订单原来是 `close_mode=AUTO`，系统自动恢复为 `close_status=OPEN`、`close_mode=NULL`。

手动关闭规则：

- 当销售订单仍有未出库数量，但客户接受少发、不再补发时，允许用户手动关闭整单。
- 手动关闭必须填写原因，写入 `close_mode=MANUAL`、`close_reason`、`closed_by`、`closed_at`。
- 手动关闭后不能继续下推发货通知或销售出库，但未出库数量仍保留真实值。例如数量 100、已出库 80、未出库 20 时，关闭状态显示“手动关闭”，未出库数量仍显示 20。
- 反关闭只允许 `close_mode=MANUAL` 的销售订单，反关闭后清空关闭模式和关闭人/时间。

行关闭处理原则：

- `line_close_status` 字段暂时保留，兼容历史数据和旧脚本，不在本轮删除。
- 销售订单前端不再把“行关闭/反关闭”作为员工可见的新业务动作，也不在分录表突出展示行关闭作为核心状态。
- 销售订单行关闭 API 已禁用，新业务不应再主动产生销售订单行关闭。后端源单守卫中仍可能保留 `line_close_status` 作为兼容守卫残留；是否全局移除行关闭另开任务。

## 前后端责任

- 后端是最终裁判：`BillLifecyclePolicy` 负责单据能力分类，`BillLifecycleService` 负责状态转换守卫和源单可执行守卫。
- 作废必须由前后端同一策略控制。前端 `documentLifecyclePolicy.ts` 控制按钮显示，后端 `BillLifecyclePolicy.requireVoidAllowed` 必须再次校验 `voidAllowed`，不能依赖前端隐藏按钮。
- 前端只做预判和体验：`documentLifecyclePolicy.ts` 负责按钮显示、禁用和状态章文案，不能代替后端校验。
- 列表批量动作和单据详情动作必须共用同一份单据能力口径；不能出现详情页无关闭按钮、列表页却能批量关闭的情况。

## 新增单据生命周期接入门禁

新增正式单据、新列表、新动作按钮之前，必须先补一条生命周期登记记录。没有登记生命周期能力的单据，不允许新增审核、反审核、作废、关闭、冻结、红冲、下推、选源等生命周期按钮。

登记记录必须明确以下字段：

| 字段 | 要求 |
| --- | --- |
| 单据类型 | 前端 `DocumentType`、后端 target type 和业务中文名必须能互相对应 |
| 列表 key | `DataListPage` 使用的 list key；如果暂未建列表，写明暂不显示列表批量动作 |
| 详情页/表单组件 | 必须默认走 `StandardDocument` / `DocumentForm`；例外要写回收条件 |
| 后端 AppService / Controller | 写清负责保存、审核、反审核、删除、作废、下推的入口 |
| 是否支持审核 | 不支持审核的页面不得显示审核按钮 |
| 是否支持反审核 | 反审核必须回退审核产生的业务事实 |
| 反审核目标状态 | 默认必须是 `DRAFT`；`REVERSED` 只能写为历史兼容展示状态 |
| 是否支持作废 | 前端 `documentLifecyclePolicy.ts` 和后端 `BillLifecyclePolicy` 必须一致；后端必须强校验 |
| 是否支持关闭 | 只适用于连续执行类单据 |
| 是否支持冻结 | 只适用于连续执行类单据 |
| 是否支持行关闭 | 必须有行级状态字段和后端守卫 |
| 是否支持行冻结 | 必须有行级状态字段和后端守卫 |
| 是否支持红冲 | 只适用于库存/财务事实类单据，且后端必须有真实红冲业务 |
| 是否允许下推 | 必须列明生成哪类下游单据 |
| 下推/选源事实字段 | 必须使用未执行数量、未出库数量、未入库数量、可下推数量、关闭/冻结状态等事实字段 |
| 历史兼容状态 | 如 `REVERSED`、旧单据状态文案等，只能用于读取和展示，不作为新逻辑目标 |

接入步骤：

1. 在本节补齐生命周期登记记录和能力判断。
2. 在后端 `BillLifecyclePolicy` 登记单据能力。
3. 如需共享生命周期 API，在 `BillLifecycleController` 登记目标表、分录表，并在 `DocumentPermissionPolicy` 登记唯一权限映射。
4. 在前端 `documentLifecyclePolicy.ts` 登记同一份能力。
5. 单据详情页通过 `StandardDocument` / `DocumentForm` 使用统一动作按钮。
6. 列表页通过 `DataListPage` 的 `documentActionTypeByListKey` 接入同一能力。
7. 下推、选源和批量动作只能依赖事实字段；`outStatus` / `inStatus`、已出库/已入库等展示状态不得作为核心判断。
8. 后端 API 不能只依赖前端隐藏按钮，必须重复校验权限、状态、能力和下游影响。
9. 添加或更新测试，至少覆盖草稿不可关闭/冻结、未审核源单不可执行、事实类单据不显示关闭/冻结、红冲仅事实类单据可见、作废受 `voidAllowed` 后端守卫控制。
10. 运行 `node scripts/a124-lifecycle-contract-scan.mjs`。该脚本是第一层静态门禁：前后端能力不一致、单据权限映射或运行时 wiring 缺失、列表动作未登记、反审核写回 `REVERSED`、展示状态驱动下推、批量动作占位等情况必须失败；同时必须有真实 HTTP 负向测试，静态扫描不能替代 401/403 和零副作用证据。
