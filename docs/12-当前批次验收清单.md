### 已确认：材料报废库存语义与首版重发边界

现有真实证据只证明：已审核生产领料单可下推材料报废单；行带出可报废数量和默认关闭的“是否入库”；材料报废审核后出现独立“报废入库”动作。证据明确把库存/成本影响列为未验证。

用户已于 2026-07-14 确认以下库存口径；“报废重发”按不产生未授权下游单据的首版最小边界冻结：

- 材料已经在生产领料审核时从原材料仓扣除，因此材料报废审核只占用来源领料行的可报废数量并进入统计，不再次扣库存。
- `是否入库=false`：审核后不产生库存流水。
- `是否入库=true`：审核后仍不自动入库，由用户执行独立“报废入库”动作，把同一物料按报废数量入指定报废仓；该动作写真实库存流水并幂等。
- 已报废入库时先阻断反审核；必须先反向撤销报废入库，再反审核报废单。
- 保存草稿允许行报废数量 `scrapQty = 0`，但禁止负数；草稿为 0 时报废原因不必填写。审核时重新校验每行 `scrapQty > 0`。
- “报废重发数量”第一版只记录并校验 `0 <= 重发数量 <= 报废数量`，不自动生成生产领料单；这是避免未授权写入的保守边界，后续自动重发另立范围。
- 不推断废料售价、成本或新物料转换，不写无依据金额。

- 达到 `10^width-1` 后精确 409，规则计数不推进；12 位宽仍不得发生 Integer 溢出。
- 禁用规则阻断新编号但不破坏既有单据；重新启用从安全最大值继续。

- 反审核新增反向流水并关联原流水，不删除/覆盖历史；余额与流水同事务。
- 库存更新后的真实余额由同一事务返回并落 `qty_on_hand_after`；禁止在报表查询时用当前余额倒推每行历史结存。
- 同一 accountSet+商品+仓库的所有正式/受控库存写入必须先确保并锁定余额行，再在锁内读取旧余额、计算 delta、更新余额并写流水；期初绝对值保存也不得在锁外读取旧余额。两个都成功的并发写入必须满足最终余额=基线+流水 delta 之和，最后一条 `qty_on_hand_after`=最终余额。
- 期初绝对值保存不得清零或覆盖既有 `qty_reserved`；锁内必须保持 reserved 不变，仅令 `qty_on_hand=newQty`、`qty_available=newQty-existingReserved`。若 `newQty < existingReserved` 精确 409，余额/流水/业务成功日志零变化；HTTP 层仍须按 A136 统一失败审计仅新增一条 `SECURITY/WRITE_FAILED`，不得为满足“零变化”而绕过失败审计。已有预留在合法期初保存后仍可正常出库或释放。
- 新库存事实的 `occurred_at` 必须在取得余额序列化锁后用数据库 `clock_timestamp()` 显式写入，不能依赖 PostgreSQL `now()`/列默认的事务开始时间；两个都成功的并发过账按 `occurred_at,id` 排序时，`qty_on_hand_after` 必须与实际余额更新顺序一致。
- 新 EXACT 来源若业务表只有 timestamptz `created_at` 可作为日期依据，必须固定按 `(created_at AT TIME ZONE 'Asia/Shanghai')::date` 推导；Opening CONTROLLED 的 `source_bill_date` 必须由同一 fact `clock_timestamp()` 按 Asia/Shanghai 推导，不能使用 UTC session 的 `CURRENT_DATE`。UTC 跨日与不同 session TimeZone 夹具必须证明 EXACT/HEADER_ONLY/CONTROLLED 日期一致。
- `trace_quality` 枚举固定为 `EXACT/CONTROLLED/HEADER_ONLY/LEGACY/TEST`：`EXACT` 具有真实 header+line，可精确钻取；`CONTROLLED` 是受控期初等真实非单据来源，可作为正式库存事实显示，但不得伪装成业务单据行或生成假钻取；`HEADER_ONLY` 只能定位到真实 header，不能宣称精确到行；`LEGACY` 不可精确定位。
- 历史库存业务事实（商品、仓库、数量、动作、来源头、单号、日期、发生时间、结存和 reversal 关系）不可改写。唯一允许的追溯元数据变更是：源单反审后保存将更新或删除旧源行时，必须在同一 routed 事务且源行删改前，把引用这些旧 line id 的历史 `EXACT` 单向降级为 `HEADER_ONLY` 并清空 `source_bill_line_id`；保留真实 header/id/no/date，禁止把旧事实 retarget 到新行或改写旧业务字段。重新审核只为新当前行写新的 `EXACT`。
- 所有既有源单 `saveDraft` 必须先锁定 header 并原子确认当前状态为 DRAFT；AUDITED/VOID 等非 DRAFT 直接保存精确 409，且 header/line/库存流水/余额/业务成功日志全部不变；HTTP 层仍须按 A136 统一失败审计仅新增一条 `SECURITY/WRITE_FAILED`。追溯降级只能在该 DRAFT guard 成功后、旧行删改前发生；正常路径必须先反审核回 DRAFT 再保存，禁止用 upsert 把 AUDITED 偷改回 DRAFT 后重复过账。
- 已存在任一历史库存流水的源单 header 不得物理删除；只有从未审核/过账的 DRAFT 才可删除。删除必须 `SELECT ... FOR UPDATE` 锁 header，锁内检查 DRAFT 与零历史流水，最终 `DELETE ... WHERE status='DRAFT'` 且 rowcount=1；与审核并发时只允许“删除先完成则审核无事实”或“审核先完成则删除 409 且 header/fact 保留”，绝不允许 orphan fact。VOID 若保留 header/line 可以沿用领域生命周期，但不得造成历史 EXACT 指向已删/改行。
- migration 只按受控 source prefix + 唯一 billNo 回填可唯一定位的历史 header；绝不按商品+数量猜 line。其余历史保留并标记对应质量。`TEST` 永不作为正式报表业务事实，生产报表 SQL 默认排除；不可生成精确钻取。
- 在 F042 正式报表可纳入的流水中，`source_bill_date IS NULL` 只允许用于迁移保留的 `LEGACY` 历史流水。固定 SQL 对这些行显式使用 `(occurred_at AT TIME ZONE 'Asia/Shanghai')::date` 作为“历史记账日期降级”参与日期筛选和显示，响应 `dateBasis=POSTING_FALLBACK`；其他正式行返回 `dateBasis=BUSINESS_DATE`。既有 `TEST` 可保留空日期，但必须在日期/fallback 计算前排除，绝不进入 rows/count/totals/export；新增 `EXACT/CONTROLLED/HEADER_ONLY` 必须有业务日期。页面/CSV 必须提示“历史记账日期（业务日期缺失）”，不得冒充或写回源单业务日期，也不得把该例外扩展到新流水、TEST 或其他报表。UTC 跨日边界夹具必须证明 count/rows/totals/export 不受 PostgreSQL session TimeZone 影响。
- 为全账套时间分页补 `(account_set_id, source_bill_date DESC, occurred_at DESC, id DESC)`；大表 migration 必须有锁/索引策略，禁止无界 Java 回填。

## F029 销售报表

### 销售明细

- report key `sales-detail`；来源为 `sales_out.status IN ('AUDITED','RED_REVERSED')` 与已审核销售退货头行。RED_REVERSED 只作为 legacy effective red 状态；销售出库 qty/amount/tax/priceTaxTotal 使用行内既有正负号，绝不再次取反。DRAFT/REVERSED/VOID 不进入。
- 过滤：业务日期、单据类型/单号、客户、商品、仓库、币种。
- 列：日期、单号、类型、客户、商品、规格、仓库、单位、数量、单价、金额、税额、含税金额、币种。
- 退货数量/金额/税额/含税金额全部负向；钻取到真实出库/退货单。

### 销售汇总

- report key `sales-summary`；单一 key 使用 `dimension=CUSTOMER|PRODUCT_UNIT`，服务端默认并 echo `CUSTOMER`。两种维度都必须在 fact 层聚合前复用销售明细的日期、AND 多词 keyword、客户、商品、仓库、单据类型与币种 predicate：CUSTOMER 按客户+币种只汇总金额、税额、含税金额，不返回数量合计；PRODUCT_UNIT 按商品 id+单位快照+币种汇总数量、金额、税额、含税金额，禁止跨单位或币种相加，显示名称不进入身份 tuple。dimension 作为受控默认/绑定值选择固定 result aggregate 分支，不得拼 SQL；汇总后不得补滤。
- CNY/USD 分行/分 totals；不提供无汇率总计。

### 销售订单跟踪

- report key `sales-order-tracking`；来源为已审核销售订单行及真实下游出库/退货数量。
- 列至少包含订单数量、已执行、已出库、已退货、未执行、已执行未出库、预计交期、剩余发货天数、行执行/出库状态。
- 令 `N`=按来源订单号+行号聚合的已审核发货通知数量，`O`=按订单号+行号聚合的有效销售出库 signed 数量（AUDITED/legacy RED_REVERSED，保留行符号），`D`=`O` 中未匹配到有效已审核发货通知来源的 legacy 直接出库 signed 数量，`R`=已审核销售退货经 `source_out_line_id` 回溯到订单行的正数量。固定公式：`executedQty=N+D`、`shippedQty=O`、`returnedQty=R`、`netDeliveredQty=O-R`、`unexecutedQty=max(orderQty-executedQty,0)`、`executedUnshippedQty=max(executedQty-shippedQty,0)`。
- 下游数量必须来自正式审核事实和统一占用口径；缺 trace 不得按商品+数量猜配，订单行自身 shipped counter 只用于回归对账、不得替代真实下游聚合。max 只用于派生待执行量，超订单、负数或 shippedQty>executedQty 等原始异常必须返回 `INCONSISTENT`，不能静默隐藏。
- 日期范围只过滤订单业务日期；下游数量表示查询时当前状态，不伪装成历史 dateTo 时点快照。`remainingDeliveryDays=planDeliveryDate-(CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Shanghai')::date`；tracking 不做跨单位 totals。

## F091 应收/应付报表

### 后端与权限

- `receivable-detail/summary` 与 `payable-detail/summary` 四个 report key 类级要求 `finance.report.view`。
- 现有 `receivable-list/payable-list` 若保留为 catalog owner，必须显式纳入后端权限 guard 并切换到真实 report 定义；不得继续依赖默认 adapter。
- 只读取销售出库过账生命周期写入的 `ar_receivable` 正负事实行、采购入库/退货过账生命周期写入的 `ap_payable` 正负事实行、A141 正式收付款核销及反审核事实，以及 A142 `sales_return_finance_allocation` 的冲应收/待退款状态；未审核源单不会生成 AR/AP 事实，因此不进入首版。
- `ar_receivable.status/ap_payable.status` 只有 `OPEN/PART_SETTLED/SETTLED`，表达结算进度而非审核状态；禁止使用 `WHERE ar_receivable.status='AUDITED'` 或 `WHERE ap_payable.status='AUDITED'`，也禁止据此排除已结清事实。

### 明细/汇总公式

- 应收按客户+币种，明细只保留销售出库审核/反审/红字/红字反审过账形成的 AR 正负事实、A141 收款核销/反审核，以及 A142 销售退货 finance allocation 的冲应收/待退款状态；汇总提供期初、应收发生、已收、退货冲减、期末。AR 事实必须保留 `ar_receivable.amount` 的原始正负号，禁止再按来源类型重复取反；A142 不得虚构 `ar_receivable` 行。
- 应付按供应商+币种，明细只保留采购/采购退货正式过账形成的 AP 正负事实和 A141 付款核销/反审核；汇总提供期初、应付发生、已付、期末。AP 事实必须保留 `ap_payable.amount` 的原始正负号，禁止再按来源类型重复取反。
- 应收余额事件增量固定为：带符号 `ar_receivable.amount`，减去已审核收款父单 allocation 的 `settlement_amount`，再减去已审核销售退货 finance allocation 的 `offset_amount`；应付余额事件增量固定为：带符号 `ap_payable.amount`，减去已审核付款父单 allocation 的 `settlement_amount`。A142 退货只通过 finance allocation 进入，禁止再生成或读取一条所谓“退货 AR”重复冲减；`pending_refund_amount` 只作为待退款状态单独展示，绝不进入 AR 余额或现金流。
- 期间明细必须由事件日期和父单当前状态重建：AR/AP 发生按来源 `bill_date`；A141 收付款核销只取 receipt/payment parent header `status=AUDITED` 的 allocation，日期取 parent `bill_date`，反审核后 parent 回 `DRAFT` 则该事件退出；A142 冲应收/待退款只取 `sales_return.status=AUDITED` 的 finance allocation，日期取 return `bill_date`。
- 期初=所有 `dateFrom` 之前上述事件增量之和，期间=`dateFrom..dateTo` 上述事件增量之和，期末=期初+期间净额，全部按 CNY/USD 分组。禁止使用 AR/AP 当前 `received_amount/paid_amount/return_offset_amount` 快照重建期初或期间，也禁止同时读取快照与 allocation 重复扣减。
- 实际收款退款单/付款退款单、预收/预付、其他应收/其他应付和任何未交付资金事实都不属于 A150；禁止为填报表空缺而伪造业务行。
- A141 正式收付款审核/反审核及 A142 退货冲应收/反审核后，明细与汇总必须同步变化。
- 同条件汇总必须等于明细 SQL 聚合；CNY/USD 分组且不混算。

### 来源、反审核与入库

- 源领料必须已审核、未关闭/冻结，且“非红字”同时满足自身 `red_source_bill_id IS NULL` 与 `NOT EXISTS (red.red_source_bill_id=source.id AND red.status<>'VOID')`；已存在红冲草稿、已审核红字或红字反审核态的原领料都不得继续下推报废。preview/list 用同一 predicate 过滤，push/save/audit 必须在锁定来源领料头后重新校验，不能只相信页面快照。存在任何非 VOID 材料报废单时阻断源领料反审核、红字反审核或作废，必须先处理下游。
- workshop 身份不得沿用 MaterialIssue 详情的 `COALESCE(...,'生产部')` 展示兜底。初次 preview/push/new draft 必须在当前 routed tenant 内把来源 task.`department_code` 精确解析为 `md_production_department.code` 且 `enabled=TRUE AND audit_status='AUDITED'`，再保存 workshop id/code/name 快照；缺失、空值、重复或初次创建时已停用/未审核一律 409，不得伪造“生产部”、跨 schema 查找或仅用名称作汇总 identity。已有 draft 的 save/audit 只校验锁内 source department code 与已存 workshop identity 一致并保留原快照，不因车间后来停用或改名而改写历史或无依据拒审；已审核报废历史继续使用保存的 workshop id/code/name 快照。
- 删除草稿释放占用；审核的业务状态与业务成功日志必须在同一 routed 事务内原子提交，事务失败时二者一并回滚；HTTP 层只按 A136 在独立事务新增一条 `SECURITY/WRITE_FAILED`，不得在业务事务外补写成功日志。
- 作废只允许 DRAFT（已审核单必须先撤销报废入库并反审核回 DRAFT）；成功作废后状态为 VOID，统计和库存流水均为 0，不再占用可报废数量，并立即释放对源领料反审核、红字反审核或作废的下游阻断。VOID 不得恢复或再次审核。
- `materialScrap` 必须同时登记到 lifecycle protocol、`BillLifecycleController` target、`DocumentPermissionPolicy=production.document.audit`、后端 `BillLifecyclePolicy` 和前端 `documentLifecyclePolicy.ts`，能力固定 close/freeze=false、line close/freeze=false、redReverse=false、void=true；audit/reverse/stock-in/reverse-stock-in 仍走 MaterialScrapAppService 专用事务。作废使用共享 `/api/document-lifecycle/materialScrap/{billNo}/void` 的 hardened reason/password/permission 流程；`BillLifecycleService.voidBill` 对 `production_material_scrap` 必须先锁 header，再用专用 helper 拒绝非 DRAFT 或仍有 active 报废入库的单据，但不得因已完整撤销的历史库存流水永久阻断作废。VOID 状态、源阻断释放和成功日志同事务；失败业务零副作用并由 A136 记录唯一失败审计。关闭/冻结/行级动作必须由 policy 返回 400，禁止另开 dedicated void 分支绕过共享守卫。
- 材料在生产领料审核时已扣库，因此报废审核只形成生产损耗事实并占用正式报废配额，绝不再次扣减库存。
- `isStockIn=false` 全生命周期零库存流水；`isStockIn=true` 审核后仅进入“待报废入库”，由独立“报废入库”动作把同一物料按报废数量入指定报废仓。报废入库与撤销报废入库都必须以整单为边界原子处理全部 `isStockIn=true` 行，不提供选行或部分成功；该动作必须幂等写真实 `inv_stock_txn` 并绑定报废单/行，“撤销报废入库”新增每行精确反向流水，任一行失败则状态、余额、流水和业务成功日志整单回滚，HTTP 层仍按 A136 记录唯一失败审计。
- 报废入库/撤销的锁序固定为报废 header→报废 lines→按 `(productId,targetWarehouseId,lineId)` 稳定排序后调用库存过账；不得按前端行顺序锁多个库存维度，避免两张报废单交叉物料/仓库时形成死锁。
- 有报废入库未撤销时阻断报废单反审核；成功反审核后统计剔除且源可报废量恢复。
