## 当前批次：A139 未知列表 Fail-Closed 与错误入口收口

### 任务坐标

- 本批只处理 roadmap item 6：未知列表不能再返回销售订单数据，错误入口必须隐藏或接入真实精确合同。
- A138/item 5 已达到 A4；开工基线固定为 `cf1756e2`。6A–6E 仍只允许只读预审，不夹带账号/员工、资金单据、销售退货、Excel 导入或新报表实现。
- 用户此前“按建议删除”只授权 A137 的 7 条孤儿数据；本批删除的是代码中的三个人工测试后门和 catalog 中六个明确未交付入口，不以该数据授权作泛化依据。

### 已确认缺口

1. 前端 `fallbackDefinition` 复用销售订单列；未定义 listKey 仍能渲染为“标准列表”。
2. `ListQueryContractRegistry` 通过 `*-master-list`、`*-source-selector` 通配和 default 合同认可未知 key；`StubListSeedRowsProvider` 的 default 直接返回销售订单行。
3. `SourceSelectorListQueryAdapter` 对未知 selector 返回 200 空集，未形成统一 404。
4. `standard-list`、`error-list`、`permission-denied-list` 是生产代码中的人工测试后门，分别承担扩容、500 和 403 伪状态。
5. 六个 catalog 入口没有真实前端定义/后端数据合同，当前可能落入销售订单兜底：`sales-detail-report`、`sales-profit-report`、`stock-flow-report`、`scrap-report`、`ar-summary-report`、`coding-rule-list`。
6. `stock-count-form-list`、`stock-count-gain-form-list`、`stock-count-loss-form-list` 有真实页面和明细查询，但 header 未登记真实 provider 分支，会落入销售订单数据。
7. `purchase-summary-report`、`task-track-report` 是已发布真实查询，但 catalog/后端缺少明确读权限；报表“查询”动作还会错误拼出 `*-report-list`。
8. A128 静态扫描仍识别旧 `assertReadable(listKey)` 签名，动态回归仍依赖 `permission-denied-list`，无法证明真实权限。

### 固定执行顺序

query 与 export 必须执行完全相同的顺序：

1. 会话认证由现有全局安全链完成；
2. `ListQueryContractRegistry` 对完整 listKey 做精确登记校验，未知立即 404；
3. 对已登记 key 执行 list-specific 权限，缺权限返回 403；
4. 只有通过前两层后才能选择 adapter/provider 并访问数据库；
5. 执行查询、筛选、分页或导出。

随机普通 key、随机 `*-master-list`、随机 `*-source-selector` 和三个退役测试 key，在管理员与低权限用户下都必须先得到 404；不得因用户权限不同泄漏“该 key 是否像某类列表”，不得触发 adapter、provider 或 JDBC。

### 精确列表与后端合同

1. Registry 只能认可显式 key 集合；suffix 只可用于已登记 key 的归类，不能作为“已知”的判断条件。
2. 未知 Registry key 抛 404；provider 的 default 不得返回 `salesRows`，source-selector 的 default 不得返回空 SQL。若前置精确门禁失效，二者仍必须 fail-fast。
3. `standard-list`、`error-list`、`permission-denied-list` 从生产 main 中完全删除；测试只能把它们作为未知 key 断言 404，不能继续保留 403/500/1200 行语义。
4. 不修改 Controller/ListQueryService 的职责边界：Controller 保持 state guard → query service，StateGuard 首先委托 Registry 校验已知 key，再执行权限。
5. 本批真实权限复用既有权限码，不新增权限：
   - `purchase-summary-report` → `purchase.order.audit`
   - `task-track-report` → `production.task.audit`
   - `stock-count-form-list` → `inventory.stock_count.audit`
   - `stock-count-gain-form-list` → `inventory.stock_count_gain.audit`
   - `stock-count-loss-form-list` → `inventory.stock_count_loss.audit`
6. operation log 的 scope 权限和其他既有列表合同保持原语义；不借本批做全量列表 RBAC 重构。

### 三个盘点 header 合同

1. `stock-count-form-list` 的 header 字段固定为：`billDate/billNo/businessType/status/department/productCode/productName/warehouse/unit/netWeight/grossWeight/systemQty/countedQty/diffQty`。来自 `stock_count` 和代表性首行，不得出现 `customer/customerCode/priceTaxTotal/outStatus`。
2. `stock-count-gain-form-list`、`stock-count-loss-form-list` 的 header 字段固定为：`billDate/billNo/sourceBillNo/status/productCode/productName/warehouse/unit/netWeight/grossWeight/qty/amount`。分别来自真实盘盈/盘亏 header + line，并关联来源盘点单。
3. header 与 detail 都必须维持当前 tenant data scope；不改盘点审核、下推、库存流水或余额语义。

### 前端与入口合同

1. 删除 `fallbackDefinition`；未知前端 listKey 不得取得销售订单列或渲染“标准列表”，应由调用边界显示明确不可用状态或拒绝打开。
2. 从 `moduleCatalog` 删除六个未交付入口，不实现它们，也不以空表/销售数据冒充报表。
3. 同步 `feature-delivery-status`：F029/F042/F061 转为 hidden + none + 空 catalog IDs；F091 只移除 `ar-summary-report`；F093 只移除 `coding-rule-list`。不提高任何 feature level。
4. `purchase-summary-report` 和 `task-track-report` 保留真实 entry id；点击名称或“查询”都打开原 key，不能拼接 `purchase-summary-report-list` 或 `task-track-report-list`。
5. 两个报表 catalog 权限分别补 `purchase.order.audit`、`production.task.audit`；低权限角色菜单不可见，直接 query/export 仍由后端返回 403。
6. 可见 queryable catalog entry 必须有唯一 delivery-status owner、明确前端 definition、精确 backend contract、adapter/provider 和权限处置；internal alias/source-selector 必须进入显式内部集合，不能靠通配/default。

5. 三类盘点准备唯一编号，header 只命中各自真实表和固定字段；浏览器截图能看见盘点编号、来源/数量，不出现客户、销售单号或含税金额。
