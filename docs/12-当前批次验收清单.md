### 已确认的三个决定

用户于 2026-07-13 明确确认：

1. **员工—账号关系**：一个用户在一个账套最多关联一个员工，同一员工在该账套最多关联一个用户；员工与账号允许各自独立存在；员工禁用不自动禁用账号。
2. **员工部门**：首版使用可选文本 `department`，不外键到 `md_production_department`，因为后者只代表生产车间，不能承载销售、采购、财务等组织。
3. **财务账户边界**：首版支持 `CASH/BANK/DEPOSIT`，每个账户固定选择 `CNY` 或 `USD`；不维护余额、期初余额、汇率、币种换算或跨币种结算。A140 交付正式选择器，真正被收付款单消费留到 6B。

### 数据模型

#### 员工主档

`md_employee` 为 tenant-owned 主数据，至少包含：

- `id/code/name/position/department/phone/email/remark`
- `enabled/audit_status/version/created_at/updated_at`
- tenant 内 `code` 唯一，编码创建后不可修改
- `audit_status` 只允许 `DRAFT/AUDITED`
- 手机、邮箱均可空，不保存登录密码或平台角色

员工登录关联不放在 tenant 表。平台 `sys_user_account_set` 新增可空 `employee_code`：

- 现有 `(user_id, account_set_id)` 唯一约束保证账号在账套内最多一个关联值
- 新增 `(account_set_id, employee_code)` 非空条件唯一索引，保证同一员工不被多个账号关联
- 不建立跨 schema FK；关联/解除时在当前 tenant 中显式验证员工存在
- 禁用员工不级联修改 `sys_user.enabled` 或 grant enabled
- 关联接口不得接受客户端传入 `accountSetCode`；账套只能从已认证 current session/TenantContext 推导，目标用户必须已拥有当前账套 grant
- 关联更新携带 grant `version` 做 CAS，并携带当前会话返回的 opaque `scopeToken`；token 绑定平台库中的 session + 当前账套权威行且每次切换账套都轮换，跨账套参数、旧 scope、会话与 grant 错配、重复员工或旧版本均拒绝且平台 grant/tenant 业务数据零写入
- `version` 必须是非负 JSON 整数且能无损转换为 64 位整数；小数、高精度伪整数和越界整数必须在进入 service 前返回 400
- 撤销账套 grant 时必须在同一平台事务清空其 `employee_code` 并向原 tenant 写 `UNLINK_EMPLOYEE_ACCOUNT`；禁用 grant 不得继续占用员工唯一索引，日志失败必须整体回滚

#### 财务账户

`md_financial_account` 为 tenant-owned 主数据，至少包含：

- `id/code/name/account_type/bank_name/account_no/account_holder/currency/remark`
- `enabled/audit_status/version/created_at/updated_at`
- `account_type` 只允许 `CASH/BANK/DEPOSIT`，`currency` 只允许 `CNY/USD`，每条账户记录只能选择一种币种
- `account_no` 使用字符串保存，保留前导零
- CASH 不填写银行字段；BANK/DEPOSIT 必须填写开户行、账号和户名
- 不包含余额、可用余额、期初余额、汇率或多币种明细；不允许一个账户同时声明多个币种

### 评审后范围扩展

原合同只列员工关联 service 不足以在真实切换点轮换账套 scope，也不足以防止不同 Spring Session wrapper 或不同实例并发穿透。独立 review 因此要求把以下三条加入 `allowedPaths`，本文件 front matter 已同步：

- `backend/src/main/java/com/jdy/erp/system/security/CurrentSessionService.java`
- `backend/src/test/java/com/jdy/erp/system/security/CurrentSessionServiceAccountSetAuthorizationTest.java`
- `backend/src/main/resources/db/migration/V101__session_account_scope_authority.sql`

`scopeToken` 必须在登录和每一次账套切换的真实写入点生成；平台库的 `sys_session_account_scope` 是唯一安全权威，session attributes 只负责向当前请求发布快照。关联更新在同一个平台事务中 `FOR UPDATE` 锁住权威行后再校验 token、更新 grant 和写租户日志；切换账套更新同一行，因此跨 wrapper、跨实例也只能确定性串行。权威行更新与切换日志提交成功后才发布 session 快照，注入日志失败时数据库与 session 都保持旧账套。对应测试使用两个不同 `MockHttpSession` wrapper 模拟同一逻辑会话，证明 switch/link 互斥、A→B→A 每次轮换、缺 token、旧 token、严格 version、撤销 grant 释放员工和切换事务回滚均 fail-closed。员工关联集成测试最终为 `11/11`。

### 主数据生命周期合同

员工和财务账户统一支持：

1. 新增：默认 `DRAFT`，重码 409。
2. 更新：只允许带 `version + changes` 的字段白名单 PATCH；旧 PUT 返回 405。
3. 查看：列表和详情返回真实 `version`，敏感字段按权限处置。
4. 审核：DRAFT → AUDITED；只有已审核且启用记录能进入选择器。
5. 反审核：AUDITED → DRAFT；已被正式业务引用后的阻断规则留到首次消费它的业务批次。
6. 启用/禁用：使用正式 status 动作，不允许通过 PATCH 篡改。
7. 不开放删除动作；不得把“删除”实现成未声明的硬删除或跨域级联。
8. PATCH 旧版本 409，审核态编辑 409，任一校验错误整笔回滚且版本不变。
9. `DELETE /api/master-data/employee/{code}` 与 `DELETE /api/master-data/financialAccount/{code}` 固定返回 405，业务状态、版本和成功日志均不变化；统一异常处理各写一条脱敏 `WRITE_FAILED`，禁用只能走正式 status 动作。

### 操作日志与隐私

以下成功动作必须写操作日志：创建、PATCH、审核、反审核、启用、禁用、员工关联、解除关联。

- 主数据日志只记录类型、编码、动作、字段名和版本，不记录手机号、邮箱、银行账号或户名原值。
- 关联日志记录 user、accountSet、employeeCode 的关系变化，不记录密码、session token 或 Cookie；撤销账套授权触发的自动解除必须标记 `source=grant_revoked`。
- 旧 PUT/DELETE 等受控拒绝由统一异常处理各写一条 `WRITE_FAILED`；失败日志只能记录 endpoint、状态码和脱敏原因，不得被误述为“操作日志不变化”。
- 权限拒绝继续由现有统一门禁审计，不新增匿名读取接口。
