## 当前批次：A138 主数据稀疏 PATCH 与并发保护

### 任务坐标

- 本批只处理 roadmap item 5：物料、客户、供应商、仓库四类主数据的编辑保存语义。
- A137 已达到 A4；开工基线固定为 `a476ecba`。item 6、6A–6E 仍只允许只读审计，不夹带生产实现或交付状态。
- 不改创建默认值、不改变审核/反审核/启用/禁用业务规则、不新增数据库列；本批只关闭更新覆盖、并发与错误反馈缺口。

### 已确认缺口

1. 两条前端编辑链都把字段定义生成的表单整体发送为 `PUT`；未展示字段不在表单内，却被后端清空、置空或重置为创建默认值。
2. 四类列表都没有返回 `version`；前端状态和更新请求也没有版本字段，两个编辑端会后写覆盖先写。
3. 后端四类 `PUT` 无条件把 `audit_status` 改回 `DRAFT`，可绕过正式反审核动作修改已审核资料；供应商、仓库等被物料引用时还可能制造生命周期不一致。
4. 后端对 JSON `null` 的多个 `.trim()` 路径会产生 500；前端又无法区分未修改、原值为空和用户明确清空。
5. 前端把所有 409 统一显示为“编码已存在”，掩盖版本冲突、审核态禁止修改和引用错误。
6. 8 个既有回归脚本把旧 `PUT` 当作“存在即覆盖并自动退回草稿”的夹具 upsert，必须迁移到正式反审核 + version PATCH，不能保留旁路。

### HTTP 与字段合同

1. 四类更新统一为 `PATCH /api/master-data/{type}/{code}`，请求体严格为：

   ```json
   {
     "version": 7,
     "changes": {
       "contact": null,
       "remark": "新备注"
     }
   }
   ```

2. `version` 必须存在且为非负整数；`changes` 必须存在且至少含一个字段。请求外层未知键、未知 type、未知字段、系统字段或生命周期字段均拒绝。
3. `code`、`systemNo`、`version`、`auditStatus`、`status/enabled` 不属于编辑白名单；编码不可在编辑中更改，启禁用和审核状态继续只走既有独立动作。
4. 字段不在 `changes` 中表示逐列保持；服务不得读取创建默认值补更新。字段显式为 `null` 时，只允许清空数据库可空列或可空引用；非空列显式 `null` 返回 400。
5. 字符串、布尔、非负数值按字段类型严格解析；空字符串只按该字段既有输入语义规范化，不得变成其他字段的默认值。
6. 物料的类别、单位、默认仓库、默认供应商、默认生产车间继续解析为已审核且启用的真实引用；引用显示值与 UUID 成对更新或成对清空。
7. 目标资料必须处于 `DRAFT`，且更新 SQL 同时匹配资料 ID/编码、请求 `version` 和 `audit_status='DRAFT'`。不存在返回 404，已审核或旧版本返回 409，任一失败时版本和所有业务列保持不变。
8. 多字段与多引用更新在一个事务内完成；任一字段或引用失败整笔回滚，不能留下部分字段已写入。
9. 成功响应至少返回 `id/systemNo/code/name/version/auditStatus/status`，前端必须用服务端规范化结果刷新本地版本。
10. 四类旧 `PUT` 在解析旧 payload 前统一返回 405，关闭全量覆盖旁路；物料类别、计量单位、生产部门等非本批类型继续保留既有 PUT，不借本批改写。

### 前端合同

1. 列表必须携带不可见的整数 `version`；打开编辑页时保存独立版本和字段原始快照。
2. 保存只比较允许编辑字段；`systemNo/code/status/auditStatus`、只读字段与未修改字段不得进入 `changes`。
3. 用户明确清空非必填字段时发送 `null`；无变化时不发送 PATCH，并给出明确反馈。
4. PATCH 成功后更新 `version`、表单规范化值和原始快照；409 保留用户输入并显示后端真实冲突原因，不得自动覆盖或静默刷新。
5. 已审核资料不能进入可保存编辑态；有未保存改动时不得审核、反审核或启禁用，必须先保存或放弃修改。
6. 客户、供应商、仓库表单中的 `status` 编辑控件在编辑态只读，状态变化继续使用正式动作。
7. 删除遗留 `useMasterDataMaintenance` 全量编辑提交死路径；正式页面与旧弹窗均不得保留第二条 PUT 更新入口。

### 自动化与浏览器验收

1. 后端对四类资料分别证明：只改一个字段时所有未声明列逐列不变；可空字段显式 `null` 清空；非空字段、未知字段、生命周期字段被拒绝。
2. 证明物料引用成对更新、无效引用整笔回滚，原值和版本均不变。
3. 证明同一旧版本第一次更新成功、第二次返回 409；已审核资料返回 409；不存在返回 404。
4. 通过真实 HTTP 证明有权限成功、无 `master.data.manage` 权限返回 403；四类旧 PUT 均返回 405。
5. 8 个依赖旧 PUT 的回归夹具迁移为：精确查询版本 → 必要时正式反审核 → PATCH → 按原脚本需要重新审核；重复执行仍可收敛。
6. 四类页面分别完成浏览器“打开编辑 → 只改一项 → 保存 → 关闭/重开确认”的可见验证，并保存截图证据。
7. 浏览器至少制造一次双编辑端冲突：先保存者成功，后保存者看到真实 409，页面保留后者未保存输入且数据库保持先保存值。
8. 前端 build、backend 全测、A115、A138 专项、manifest、`area:master-data`、smoke、full 达到冻结门槛；历史冻结失败必须逐项对照，不得新增失败。
9. 输出验收报告、独立 review 和按合同/后端/前端与脚本/测试/文档拆分的独立提交，工作区除后续目标批次外保持干净。

### 禁止事项

- 不通过前端补齐隐藏字段来掩盖后端全量覆盖语义。
- 不让 PATCH 隐式反审核、隐式启禁用或重写编码。
- 不把 `PUT` 留作四类资料的兼容后门，也不为自动化脚本开放测试专用业务旁路。
- 不在 Controller 或前端实现字段业务规则；Controller 只做请求边界与审计编排，字段校验、引用解析、CAS 和事务放在 application service。
- 不在 A138 夹带 item 6、6A–6E、库存、资金或新增主数据字段实现。
