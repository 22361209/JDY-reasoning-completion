## 当前批次：A141 正式收款单与付款单

### 任务坐标

- 本批只处理 roadmap 6B、F026、F036、F080、F082，目标 A4。
- A140/6A 已达到 A3；开工基线固定为 `8f3c6e3a`。
- F026 销售收款、F036 采购付款只是业务入口；F080 收款单、F082 付款单是 finance 域正式单据。四个 scope 必须复用同一结算能力，不能另建销售版和采购版结算引擎。
- 6C–6E 可以继续只读预审，但不得夹带销售退货、Excel 导入、报表或错误入口实现。

### 用户已确认的三个决定

用户于 2026-07-14 明确确认：

1. **能力归属**：按推荐方案，销售收款和采购付款都打开或下推 finance 域正式收款单/付款单，不在 sales、purchase 内复制结算 SQL 或生命周期。
2. **核销模型**：按推荐方案，同一结算客户/供应商的一张单据可以选择多张应收/应付来源，并可以填写多条资金账户行；不同往来单位不得混在同一单据。
3. **币种范围**：首版正式支持 `CNY` 与 `USD`。单据头、全部来源行和全部资金账户行必须同币种；不维护汇率、折算金额、记账本位币、汇兑损益或跨币种核销。

### 范围内与范围外

范围内：

- 正式收款单、付款单的新增、草稿修改、查看、审核、反审核和草稿删除。
- 同一往来单位的多来源核销、多资金账户收付、部分核销、全额核销。
- CNY/USD 原币核销；现有及历史销售/采购事实默认 CNY。销售订单/采购订单明确选择币种，发货通知、销售出库和有来源采购入库逐级继承；无来源采购入库可明确选择。财务过账把币种原样写入应收/应付。
- 销售出库、采购入库的“收款/付款”入口只预填来源并打开同一 finance 表单。
- 旧立即结算数据无损保留、旧立即结算写接口退役、权限/日志/并发/两账套隔离。

范围外：

- 收款退款单、付款退款单、预收款、预付款、无来源收付款。
- 账户余额、期初余额、资金日记账、银行对账、手续费自动生成其他支出。
- 汇率、币种换算、跨币种核销、汇兑损益和本位币报表。
- 在 sales/purchase 模块复制 finance 结算表或直接更新 `ar_receivable` / `ap_payable`。
- 调用接口即直接结算，以及为兼容旧脚本保留可绕过草稿审核的生产入口。

### 币种合同

1. `sales_order`、`delivery_notice`、`sales_out`、`purchase_order`、`purchase_in`、`ar_receivable`、`ap_payable` 增加不可空 `currency`，只允许 `CNY/USD`；升级前数据回填 CNY。
2. 新版销售订单、采购订单和无来源采购入库 UI 及 A141 新测试必须显式保存 CNY/USD；为兼容本批允许路径之外的历史 CNY 客户端和既有回归，API 省略 `currency` 时继续按 CNY 保存。显式空串或非法币种仍返回 400。发货通知只能继承其来源销售订单币种，销售出库只能继承其直接来源发货通知币种；有来源采购入库只能继承采购订单币种。任何下游客户端显式自报币种与来源不一致都由服务端拒绝。
3. 销售出库/采购入库的红字或反向事实必须继承原单币种，不能借反向动作改币种；采购退货形成的应付反向事实继承来源采购入库币种。6C 的销售退货也必须继承来源销售出库币种。
4. 收款/付款草稿只能选择与单据头相同币种的应收/应付和已审核、启用财务账户；审核时后端必须重新校验，不依赖前端过滤。
5. 同一单据任何来源或账户币种不一致都返回 409，业务状态、已核销金额、单据版本和成功日志零变化。
6. 不允许用 USD 账户核销 CNY 应收/应付，反之亦然；数值不做任何隐式乘除或换算。

上述省略币种回退只是一条旧 CNY 写入兼容窗口，不允许把未知值回退为 CNY，也不允许前端借此省略字段；A141 页面和专项证据必须证明 CNY/USD 都以显式原币代码贯穿。该窗口避免扩大 allowedPaths 批量改写约 50 个历史回归脚本，full 不得因此新增失败。

为把订单/通知/出入库头币种逐级传给 finance posting 而不让 sales/purchase 直接写 AR/AP，A141 允许给共享 `PostingContext` 增加向后兼容的可空/默认 CNY 币种字段；库存和生产现有六参数构造路径不得因此改变语义。这里只增加原币代码和继承守卫，不给报价、价格策略、库存、成本或会计本位币扩展换算能力。

### 正式单据模型

收款单和付款单各由三层事实组成：

1. **单据头**：`id/bill_no/party_id/bill_date/currency/amount/status/version/remark/created_at/updated_at/audited_at/audited_by`。
2. **资金账户行**：`line_no/account_id/payment_method/amount/fee/transaction_no/remark`；账户必须来自 A140 `md_financial_account`。
3. **核销来源行**：`line_no/receivable_id|payable_id/source_amount/settled_before/unsettled_before/settlement_amount/remark`；正式影响只使用来源 id 与本次核销金额，展示快照不得替代审核时实时校验。

固定约束：

- `status` 只允许 `DRAFT/AUDITED`，反审核回 `DRAFT`，不创建新的 `REVERSED` 状态。
- 单号继续由 `NumberingService` 生成：收款单 `SKD`、付款单 `FKD`；客户端不能指定新单号。
- DRAFT 的头金额、资金行金额和来源行金额允许为 0 或留空，但不得为负数；0 元草稿不要求填写原因。同一来源在一张单据中只能出现一次。
- 保存时资金行金额合计、来源核销金额合计和单据头金额必须精确相等；空行不落库，三者都为 0 的草稿允许保存。审核时总额和每条有效资金/来源行金额必须大于 0。预收/预付不在本批，因此不允许未分配差额。
- `payment_method` 首版只允许 `CASH/BANK_TRANSFER/OTHER`；CASH 账户只允许 CASH，BANK/DEPOSIT 账户不得使用 CASH。
- 页面保留手续费字段，但 A141 只接受 `fee=0`；非零值返回明确错误，不伪造账户余额或其他支出事实。
- 草稿修改必须提交非负 64 位整数 `version` 做 CAS；旧版本 409，任一行校验失败整单回滚。
- 来源选择器和审核只接受金额为正且仍有未核销余额的 AR/AP；红字、负数或零金额事实不在 6B 直接收付款，退款与冲销留给后续正式单据。

### 生命周期与并发合同

#### 保存草稿

- 新增只写单据头、资金行和来源行，不更新应收/应付已核销金额和状态；0 元草稿可保存且不需要原因，负数在保存前拒绝。
- 多张草稿可以引用同一来源；草稿不是正式占用，不减少其他用户可选余量。
- 修改只允许 DRAFT，并以 header `version` 做 CAS；审核态修改 409。
- 草稿可以删除；审核态不能删除。删除只清本单草稿，不修改来源或账户。

#### 审核

- 审核在一个 tenant 事务内锁定单据头，并按稳定顺序 `FOR UPDATE` 锁定全部来源应收/应付。
- 重新校验状态、往来单位、币种、账户审核/启用状态、金额相等关系和每张来源实时未核销余额。
- 只有审核成功才增加 `received_amount/paid_amount`，并把来源状态重算为 `OPEN/PART_SETTLED/SETTLED`；随后把单据置为 AUDITED、版本递增并写成功日志。
- 对同一已审核单据重复调用审核必须幂等返回当前结果，不重复增加金额、不重复写成功业务日志。
- 两张竞争草稿并发审核时，按数据库锁顺序串行；后到者若超过剩余金额返回 409，不能出现负余量、超额或半截行。

#### 反审核

- 只允许 AUDITED 单据反审核；在一个事务内锁定单据头和全部来源，按本单核销明细精确扣回 `received_amount/paid_amount` 并重算状态。
- 若来源金额、币种、往来单位或已核销金额不足以安全释放，整单 409，任何来源和单据状态均不变化。
- 成功后单据回 DRAFT、版本递增；资金行和来源行保留供修改或重新审核。
- 对 DRAFT 调用反审核返回 409；不得把从未审核的草稿误述为已反审核。

### 历史数据与旧接口

1. V5 以来的 `ar_receipt`、`ap_payment` 是“调用即核销”的旧事实。当前 public 存量及各 tenant 存量的 id、单号、来源、日期、金额和核销影响必须无损保留。
2. 迁移优先原位演进旧头表并新增账户行/核销行；必须给旧记录明确 `LEGACY` 来源标识，为每条旧事实生成恰好一条可追溯的单来源核销明细；不得伪造不存在的资金账户、交易号或操作人，也不得再次修改 AR/AP 已核销金额。
3. AUDITED legacy 记录的头和明细只读且永不允许物理删除，但允许在来源仍可安全释放时执行一次正式反审核。反审核后回 DRAFT，原往来单位、币种、来源和核销金额仍锁定；必须补齐真实同币种账户行后才能重新审核。迁移无法还原的审核人保持空或明确系统迁移标识，不伪造用户。
4. 升级前后旧记录数、主键、bill_no、金额合计和关联来源必须逐 tenant 对账一致；迁移重复执行和备份恢复不得重复生成行。
5. `POST /api/finance/receivables/{billNo}/receipt` 与 `POST /api/finance/payables/{billNo}/payment` 不再结算。已认证且有权调用时返回 410 和正式单据入口提示；匿名/无权仍先返回 401/403。任何分支都不得写业务事实或成功日志。

### API 与模块边界

正式入口固定为：

- `POST /api/finance/receipts/draft`
- `PUT /api/finance/receipts/{billNo}/draft`
- `GET /api/finance/receipts/{billNo}`
- `POST /api/finance/receipts/{billNo}/audit`
- `POST /api/finance/receipts/{billNo}/reverse`
- `DELETE /api/finance/receipts/{billNo}`
- 付款单使用同结构 `/api/finance/payments/...`

实现要求：

- Controller 只解析请求和声明权限，不直接拼接结算 SQL；正式规则集中在 `FinanceSettlementAppService`。
- sales/purchase 只能通过 finance application service 或打开 finance 页面，不得直接更新应收/应付或收付款表。
- 两类单据共用同一应用服务算法和校验器，只允许在 party/source/字段标签上参数化。
- 两个来源选择器继续走统一 `/api/lists/{listKey}` 协议，SQL 只在 `SourceSelectorListQueryAdapter` 内扩展；不在 finance Controller 增加第二套选源查询。
- 列表 key 固定为 `ar-receipt-form-list`、`ap-payment-form-list`；来源选择器固定为 `ar-receivable-settlement-source-selector`、`ap-payable-settlement-source-selector`，未知 key 继续 fail-closed。

`BillLifecycleController`/`BillLifecyclePolicy` 只登记收付款单的共享能力边界：关闭、冻结、作废、行动作和红冲全部为 `false`，通用路由必须在业务 SQL 前拒绝。这项登记不增加通用审核/反审核路由，也不允许 `BillLifecycleService` 改写收付款事实。

### 权限与操作日志

- 正式收付款列表和详情允许 `finance.report.view` 或 `finance.settle` 只读；新增、修改、审核、反审核、删除和来源/账户选择器只允许 `finance.settle`。
- `finance.report.view` 不自动获得任何收付款维护能力；财务账户 selector 继续只允许具备 `finance.settle` 的结算用户读取用于制单的数据。
- 匿名 401、无权 403 必须发生在 JDBC 业务写入前；前端菜单隐藏不能替代后端权限。
- 成功日志动作至少包括 `CREATE_RECEIPT_DRAFT/UPDATE_RECEIPT_DRAFT/AUDIT_RECEIPT/REVERSE_RECEIPT/DELETE_RECEIPT_DRAFT` 及付款对应动作。
- 日志记录真实用户、账套、单号、状态、币种、总额、来源数量和账户数量；不得记录银行账号、户名、交易号原值或 Cookie。
- 审核幂等重放不得新增成功日志；410 旧接口、权限拒绝、版本冲突、币种冲突和超额失败走统一脱敏失败审计且业务零副作用。

### 前端与可见页面

1. 应收应付模块新增“收款单”“付款单”正式列表入口；页面支持新增、查看、修改草稿、审核、反审核和删除草稿。

3. 头部显示单号、客户/供应商、日期、币种、状态、版本和备注；资金账户区与核销来源区使用项目现有表格和 ActionBar 视觉语言。
4. 来源弹窗只返回当前往来单位、当前币种且未核销金额大于 0 的来源；账户弹窗只返回当前币种的已审核启用账户。服务端仍做最终校验。
5. 明细实时显示来源金额、已核销、未核销和本次核销；草稿不得把本次金额提前计入“已核销”。

8. 1366×768 和 1920×1080 下不得横向溢出页面外；关键按钮、币种、两张表和合计必须可见。

### 自动化与浏览器验收

1. CNY 与 USD 各完成至少一条销售订单→发货通知→销售出库→应收→收款，以及采购订单→采购入库→应付→付款真实链路；每级币种一致，无换算字段或隐式换算。另验收无来源采购入库的 USD 路径。
2. 0 元草稿无需原因即可保存，负数草稿拒绝，0 元审核拒绝；新增草稿后应收/应付金额、状态和成功核销日志零变化，修改 CAS、旧版本、审核态修改和删除规则精确通过。
3. 同一客户/供应商的两张来源 + 两条账户行完成审核；不同往来单位、不同币种、账户禁用/未审核、非零手续费均被拒绝。
4. 部分核销、全额核销、超额核销和两张竞争草稿并发审核可解释；重复审核幂等且只有一次正式影响和一次成功审核日志。
5. 反审核精确释放多来源金额并恢复状态；制造任一来源不一致时整笔失败且零半截数据。
6. 旧 public 与 tenant 记录升级前后逐行/汇总对账一致；AUDITED legacy 头/明细只读且不可删除，可安全反审核释放，重新审核前必须补真实账户。两个旧立即结算 URL 对有权用户 410，对匿名/无权 401/403，所有分支零结算影响。
7. 管理员、财务、只读报表、仓库角色完成 API 和菜单权限矩阵；两个 tenant 可使用相同单号序列和账户编码而不串数据。

9. 浏览器完成收款/付款新增、两区分录、CNY/USD、保存重开、审核、幂等重放、反审核、legacy 只读和低权限菜单验收。
