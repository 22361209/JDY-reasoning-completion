# 架构决策记录

本文记录已经明确的长期架构决策。除非用户明确改变方向，否则后续开发应遵守。

## ADR-001 技术栈选择

**决策：** 使用 `Java Spring Boot 模块化单体 + Vue 3 + PostgreSQL`。

**原因：**

- 项目目标是长期替代金蝶云星辰，而不是短期原型。
- Java/Spring 更贴近企业 ERP 长期工程化路线。
- Vue 3 更适合做金蝶式复杂工作台、多页签、表格、弹窗和单据交互。
- PostgreSQL 能稳定支撑当前和未来相当长时间的库存流水、单据和报表查询。

**不选：**

- 不以 Django admin 或传统后台作为正式产品前台。
- 不以 Java 微服务作为第一版起点。

## ADR-002 第一版使用模块化单体

**决策：** 第一版使用单个 Spring Boot 应用，但按模块严格分包和分层。

建议模块：

```text
master-data
sales
purchase
inventory
production
outsourcing
finance
system
reports
```

**原因：**

- 第一版需要快速形成业务闭环。
- 当前规模不需要微服务复杂度。
- 模块化单体可以在未来拆服务时降低迁移成本。

## ADR-003 只缓存登录态

**决策：** 第一版 Redis 只用于登录态/会话，不缓存业务结果。

允许缓存：

- 登录会话
- CSRF/session/token
- 临时安全状态

禁止缓存：

- 库存余额
- 可用库存
- 单据列表
- 单据审核状态
- 应收应付余额
- 资金余额
- 报表结果

**原因：** ERP 业务中库存和资金必须以数据库事务结果为准，避免员工看到旧库存。

## ADR-004 库存以流水表和余额表为核心

**决策：** 库存必须同时维护：

```text
inv_stock_txn       库存流水
inv_stock_balance   当前余额
```

单据审核时，在同一数据库事务内写入库存流水并更新库存余额。

**原因：**

- 查询库存余额时不需要扫全部流水。
- 审核时可以做数据库级库存校验。
- 历史追溯和当前查询都能保证。

## ADR-005 预留异步事件和未来 MQ

**决策：** 第一版先使用本地领域事件和 outbox 表，不直接引入 RabbitMQ/Kafka。

示例事件：

```text
SalesOutboundApproved
PurchaseInboundApproved
ProductionMaterialIssued
ProductInboundApproved
PaymentApproved
```

**原因：**

- 当前不需要 MQ 的部署和运维复杂度。
- outbox 表可以保证业务数据和事件记录在同一事务内提交。
- 未来拆微服务时，可将 outbox 事件投递到 MQ。

## ADR-006 前端必须产品化

**决策：** 正式前端使用 Vue 3 + TypeScript，不使用后端管理后台作为员工入口。

必须支持：

- 左侧模块导航
- 顶部多页签工作区
- 列表页和单据页
- 筛选区、选择器、弹窗
- 表格列设置、固定列、批量动作
- 导入导出入口

**原因：** 视觉和手感差距主要来自前端，不来自后端语言。

## ADR-007 Java、持久化和迁移工具

**决策：**

- Java 版本：`21`。
- Spring Boot 版本：`3.5.15`。
- 持久化：MyBatis 起步。
- 数据库迁移：Flyway。

**原因：**

- Java 21 是长期维护且适合企业项目的基线。
- Spring Boot 3.5.15 来自 Spring Initializr 当前可用稳定版本。
- ERP 查询和报表会有大量定制 SQL，MyBatis 比纯 JPA 更容易控制 SQL 和性能。
- Flyway 简单直接，适合当前模块化单体阶段的数据库迁移管理。

## ADR-008 复杂表格组件

**状态：已被 ADR-011 修订。**

早期决策为正式前端复杂表格首选 `VXE Table`，从 B1 高密度列表批次开始接入。A112b/A112c 后，列表和分录已改向原生共享表格内核，VXE 不再作为新表格能力的主路线。保留本 ADR 仅作历史记录。

**原使用范围：**

- 业务列表页
- 单据分录表
- 报表结果表
- 需要列设置、固定列、批量选择、键盘录入的高密度表格

**原原因：**

- ERP 需要更接近金蝶式的高密度表格、列操作和分录录入体验。
- VXE Table 对 Vue 3、中文 ERP 场景、可编辑表格和虚拟滚动更贴近本项目首版需求。
- 第一版不从零手写大表格内核，避免后续列设置、固定列、键盘导航和性能问题变成长期债务。

**原边界：**

- B0 页面外壳允许使用原生表格做占位样式。
- 从 B1 开始，正式业务列表和单据分录逐步切换到 VXE Table。（已废止，见 ADR-011。）
- 如未来出现授权、性能或交互能力瓶颈，再评估 AG Grid，不在首版提前引入双表格体系。

## ADR-009 前端按「范式组件 + 逐入口模块」组织，禁止万能上帝组件

**背景：** 早期实现把几乎所有页面塞进单个 `App.vue`（约 4651 行）+ 单个通用 `DataListPage.vue`（约 1373 行），靠 `v-if` 大开关渲染登录、设置、单据、列表等一切。此结构既达不到逐屏 95% 还原，也使每次前端改动都吃满上下文，是 token 黑洞。

**决策：** 前端不得用单一通用组件/单一大文件渲染所有页面，采用两层结构：

- **范式组件层 `components/`**：小而精、忠实还原金蝶范式、跨入口复用。至少包含 `ShellLayout`、`FunctionPanel`、`StandardList`、`StandardDocument`、`EntryTable`（分录表格）、`Selector`、`Toolbar`、`StatusStamp`。表格能力按 ADR-011 的原生共享表格内核演进。
- **逐入口模块层 `modules/<模块>/<入口>`**：每个业务入口一份页面模块，用自己的列、工具栏、单头字段、分录、状态机、交互去**组合/配置**范式组件，匹配该入口的金蝶截图。
- 复用在组件层，**95% 逐屏还原在入口层**。
- 单个 `.vue` 控制在合理体量（建议 ≤ ~400 行）；不得再出现 `App.vue` 式上帝组件。

**与 复刻-local 一致：** 这是 `02_复刻规划/首版页面实现批次与组件复用矩阵` 标准列表/标准单据/分录表格/选择器范式的正确落法。

**迁移（债先还，对应 1+a 决策）：**

1. 冻结 `App.vue`，不再往里加任何入口。
2. 抽出外壳与范式组件；把已实现的销售/采购/库存/生产核心入口迁为逐入口模块。
3. B6 系统设置/安全/通知等已超建项各归各模块，并**冻结深度**（消息预警 P2 第二版、网络控制 P3 后续、数据权限 P2 第二版、审批流后置）。
4. `frontend/src/app/featureScope.ts` 仍由 `generate-frontend-scope.mjs` 生成，不手改。

## ADR-010 后端采用精简「单据平台骨架」，单据逻辑出 Controller

**背景：** 后端现状是单据的审核/反审核/红冲/下推/过账逻辑全写在 Controller、裸 SQL、每张单复制一遍；`shared/` 仅一个 `BillStatus` 枚举且与实际状态串脱节；财务过账与出库/入库审核脱钩。后端才 6186 行、尚无沉淀坏模式，是定骨架最便宜的时点；再铺到 40+ 张单将成为后端版 App.vue。

**决策：** 建立后端单据平台骨架（详见 `docs/14-单据平台骨架.md`），在 `shared/` + 各模块 `application/` 提供共享抽象：单据契约（表头+分录+共享列）、`BillStatus` 状态机 + 守卫式转换、`PostingPipeline`（库存 + 财务过账钩子）、`ConversionService`（下推 + 已执行/剩余量滚动）、`NumberingService`、共享基建（lookup/日志/校验）。单据逻辑从 Controller 迁到 AppService，修掉 `docs/05`/`docs/08` 违规。

**精简原则：** 抽取 K3Cloud（HW-WIN2019 解剖）验证过的可靠模式，**砍掉其重**——不做元数据驱动单据引擎、插件框架、多组织、字段级权限、单据类型元数据规则层。机制参考 `HW-WIN2019/k3cloud-system-mechanism-notes.md`。

**落地：** 先建抽象 → 先迁销售出库证一张（回归绿）→ 再迁其余 5 张 → 之后广度在骨架上实现。

**附带修复：** `BillStatus` 对齐实际状态；财务过账接到出库/入库审核（对齐 `docs/06`）；单据编号改后端生成。

## ADR-011 表格路线改为原生共享表格内核

**背景：** A112b 前项目存在两套表格方向：列表使用 VXE Table，分录使用原生 `<table>`；随后 A112b 将列表整单/明细渲染收回原生表格结构，A112c 抽出 `frontend/src/components/table/TableCore.vue`，让列表和分录共用同一个原生共享内核。

**决策：** 新增和重构表格能力只落到原生共享表格内核，不再使用 VXE Table 作为运行时表格依赖。

**原因：**

- 本项目目标是高仿云星辰/云星空的表格手感，分录行、悬浮加减、列头筛选、列头批量填充、日期单元格、键盘录入等交互需要更细的控制权。
- 当前列表和分录已经同向收敛到原生 `TableCore`，继续引入 VXE 会重新制造双表格体系。
- 原生共享内核能把列表只读渲染和分录可编辑渲染放在同一列宽、横滚、表头和密度体系里，便于逐屏贴近金蝶。

**边界：**

- 旧 `.vxe-*` 类名、`vxe-list-table` test-id 可作为回归定位兼容层短期保留，但它们只是历史命名，不代表运行时仍使用 VXE。
- `vxe-table` / `xe-utils` 不作为前端依赖保留；若以后确需引入第三方表格，必须另开 ADR 并说明为什么原生共享内核无法满足。
- 任何新列表/分录能力默认进入 `TableCore` / `EntryTable` / 标准列表范式，不新建第三套表格。

## ADR-012 多账套采用共享应用容器 + 数据库账套隔离

**决策：** 长期多账套架构采用一套共享应用容器，不按账套启动多套前后端容器。

```text
frontend 容器
backend 容器
redis 容器
postgres 容器
        |
        ├── platform_db       平台库：用户、账套列表、登录、权限入口
        ├── tenant_bld_2026   博莱德账套
        ├── tenant_test       测试账套
        └── tenant_history    历史账套
```

**登录/切换流程：**

1. 用户输入账号密码。
2. 选择账套。
3. 后端读取账套配置。
4. 当前请求绑定 `tenant/account_set`。
5. 业务操作进入对应账套数据库；附件进入对应账套目录/桶；Redis key 带账套前缀。

**为什么不做每账套一套容器：**

- 每个账套都要升级一次应用，长期版本容易漂移。
- 配置、日志、备份、恢复都会分散。
- 小公司内部 ERP 的账套隔离主要是数据隔离，不需要用容器做默认隔离边界。

**当前过渡实现：**

- A117 先落 `sys_account_set`、登录账套选择、当前 session 账套上下文、账套初始化、期初库存、编号规则。
- 编号规则、库存余额、库存流水、期初库存先带 `account_set_id`。
- 既有业务单据表仍处在单库过渡期；正式 `platform_db + tenant_*` 路由前，不宣称已完成完整多账套数据隔离。
- 切换账套只切换 session 上下文并刷新前端工作台，容器保持常驻运行，不在切换时启动/停止容器。

**边界：**

- Redis 仍只缓存登录态；未来 Redis 共用时 key 必须带账套前缀。
- 业务结果、库存、资金仍不得缓存。
- 账套初始化必须是管理员显式动作，不能在登录或切换时自动清理数据。

## ADR-013 单据生命周期采用主状态 + 关闭状态 + 冻结状态三轴模型

**背景：** 页面和列表曾经把审核状态、出库/入库执行状态、关闭、冻结、红冲等混在一起判断，导致动作按钮容易在不同单据间漂移：有些执行事实单据显示关闭/冻结，有些连续执行单据又缺少列表批量守卫。继续让每张单据自己写生命周期判断，会让 A120-A124 建立的页面协议失效。

**决策：** 正式单据统一采用三轴生命周期：

- `status`：`DRAFT` / `AUDITED` / `REVERSED` / `VOID` / `RED_REVERSED`，只表达保存、审核、反审核、作废、红冲主线。
- `close_status`：`OPEN` / `CLOSED`，只表达连续执行类单据是否停止后续执行。
- `frozen_status`：`NORMAL` / `FROZEN`，只表达连续执行类单据是否暂停后续使用。

不得新增独立 `execution_status` 作为生命周期来源。出库状态、入库状态、已执行数量、未执行数量等是执行事实或展示派生值，不能决定按钮是否合法。

**分类：**

- 销售订单、发货通知单、采购订单属于连续执行承诺，支持关闭/冻结和行关闭/行冻结。
- 销售出库、采购入库、生产领料、产品入库属于库存/执行事实，支持红冲，不支持关闭/冻结。
- 销售报价单属于报价候选，不支持关闭/冻结/红冲。
- 采购退货、其他出入库、调拨、盘点、盘盈、盘亏第一版不支持关闭/冻结/红冲。

**落地：**

- 后端 `BillLifecyclePolicy` 是最终能力表，`BillLifecycleService` 负责状态转换和源单可执行守卫。
- 前端 `documentLifecyclePolicy.ts` 只做体验层预判，列表页和详情页必须读取同一份能力口径。
- 新增正式单据时必须同时登记后端能力表、前端能力表、列表动作映射和验收规则。

**边界：**

- BOM、生产计划、生产任务、采购申请、委外链路如果尚未接入共享 `BillLifecycleController`，仍必须在各自 AppService 中遵守同样生命周期口径：保存只草稿，审核后才可被选源、下推或产生业务事实。
- 改某张单据是否支持关闭/冻结/红冲，属于生命周期协议变更，必须更新 `docs/guides/bill-lifecycle-unification-protocol.md` 与验收报告。

## ADR-014 项目范围、交付状态与回归清单采用三份可校验真相源

**背景：** 原始审批、实施例外、公开菜单、历史验收报告和本地 `verification/` 曾同时被当成“当前进度”，导致已实现、仅有入口、后端存在、真正达到 A3/A4 等状态混在一起。旧 `full` 又从 ignored 运行产物读取脚本清单，干净 checkout 无法重现。

**决策：** 项目治理固定为三类职责互斥的机器可读产物：

- `config/effective-feature-scope.json`：当前执行范围。它是生成物，只能由原始 `approved-feature-scope.json` 和手维护 `implementation-overrides.json` 推导。
- `config/feature-delivery-status.json`：交付状态。它只引用 effective scope ID，记录 A0-A4、入口处置、证据和已知缺口，不得反向改变范围。
- `config/regression-manifest.json`：回归归属。smoke / area / full 全部从这里选集；每个 `scripts/*-regression.mjs` 必须登记为 full 项或带原因的历史聚合豁免。

`docs/09` 只保存唯一当前快照，`docs/12` 只保存唯一当前任务包；历史进入 `docs/验收报告/`、`docs/archive/` 和 Git 历史。CI 与本地使用同一组 scope/status/manifest 扫描命令。

**边界：**

- 原始审批快照不可被 delivery status、catalog 或历史实现反写。
- 原始审批中的 F ID 是稳定身份，不得按 Excel 当前行号重排；导出时按既有 `module + feature` 对账，新增、删除、重命名或重复身份必须 fail closed 并先走显式范围决策。
- 缺少当前证据时使用 `unverified + knownGaps`，不能把“代码存在”猜成完成。
- 每个交付状态必须给出入口、后端、权限、日志、自动化、浏览器六类 `capabilityChecks`；没有直接证据时保守标为 `unverified`。
- 每个正式 catalog ID 必须恰好由一个 scope feature 认领，或进入带处置原因的显式 `catalogExceptions`；禁止重复认领和未登记入口。
- 第一版 P0 公开交付至少 A3；库存、资金、权限等高风险能力达到 A4 前必须保留风险说明。
- 运行结果仍写 ignored `verification/`，但清单、关键结论和验收报告必须受版本控制。
- 范围决策未确认时可以修治理工具和缺陷，但不得继续扩大对应业务功能。
- CI 必须重生成 effective scope 与正式前端 `featureScope.ts` 后检查零差异；审批 Excel 与 docs/01/02/03 因缺少仓库可安装的 artifact-tool lockfile，仍由本地 dry-run 和 scope contract 守护，不伪装成 CI 可复现。
